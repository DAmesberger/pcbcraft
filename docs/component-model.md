# Persistent component model

Implementation contract, 30 October 2026. This document says how the [accepted authoring contract](part-library-design.md#accepted-authoring-contract) is represented in the document, the engine and its consumers. It covers exactly three slices:

1. **Definitions, revisions, instances and units.** This slice replaces the monolithic `Part`, the `part.*` commands and `Instance.position`.
2. **Typed fields and quantities.** This slice replaces `Instance.value: String` and the scripting proof's `UnitDefinition`.
3. **Terminal functions and selections.** This slice replaces `PinKind`.

**Status (30 October 2026):** slices 1, 2 and 3 are implemented headlessly as described here, with the recorded deviations for [slice 1](#slice-1-implementation-notes), [slice 2](#slice-2-implementation-notes) and [slice 3](#slice-3-implementation-notes). Since 1 November 2026 the desktop authors multi-function pins in the Pins tab and assigns them in the schematic pin-mux panel; see [pin functions as built](#pin-functions-peripherals-rules-pinout-import-and-firmware-c1c7-as-built). The slices add no feature scope beyond the contract. When something is deferred, this document says so and names the scenario that owns it.

All fixtures are original synthetic data. Behavior comes from this project's specification, general electronics conventions and public specifications. No GPL/LGPL/AGPL EDA implementation, library or proprietary tool data is consulted (see [attribution](../ATTRIBUTION.md)).

## Ground rules for all three slices

- **One model, replaced in place.** Each slice deletes the type it supersedes and updates every consumer in the same change. `Part`/`PartRef`/`PartCommand` go in slice 1; `Instance.value` and `UnitDefinition` in slice 2; `PinKind` in slice 3. Old and new models never coexist. The `.pcbcraft` format keeps `FILE_VERSION = 1`, with no migrations or legacy readers. Files written before a slice fail to decode as malformed (`deny_unknown_fields`) and are never partially read.
- **One engine.** Every mutation is an `Operation` applied by `Engine::apply` at an expected revision. Every read-only report is a `Query` answered by `Engine::query`. A failure leaves document, revision and undo/redo history unchanged. UI, CLI and MCP send the same operations and queries. Programmatic calls never open dialogs.
- **Core stays pure.** `pcbcraft-core` gains no filesystem, UI, transport, Solidcraft or randomness dependency. Rhai stays inside `scripting`. Its values never appear in persisted or transported types.
- **Each rule has one owner.** Every domain rule is one named function in one module ([module map](#d-module-map)). Command handlers, the update planner and document validation call that function; none restates it.
- **No category branches.** No code tests for "resistor", "transistor", "MCU" or similar. Every behavior is driven by declared data: terminals, units, fields and functions.
- **Bounded input.** Every new collection and string has an explicit limit, checked before allocation-heavy work (see [limits](#limits)). Production code has no `unwrap`/`expect`/`panic!`/`todo!`/`unimplemented!`/`unsafe`.

## (a) What is pinned, by whom

### Identity

| Identity | Type | Allocated by | Scope |
| --- | --- | --- | --- |
| Definition lineage | `DefinitionId(Id)` | `Project::allocate` when a new draft is created | Project. One lineage has exactly one kind. |
| Revision | `Revision(u32)`, ≥ 1 | `library::publish` (base + 1, or 1) | Lineage |
| Exact reference | `ComponentRef`, `SymbolRef`, `PackageRef`, `FootprintRef`, `BindingRef` (slice 1); `QuantityKindRef`, `FieldRef` (slice 2), each `{ id: DefinitionId, revision: Revision }` | — | — |
| Local IDs | Component: `TerminalId` (slice 1), `FunctionId`, `ResourceId`, `RoleId` (slice 3). Symbol: `UnitId`. Package: `PackageTerminalId`. Footprint: `PadId`. Field: `ChoiceId` (slice 2). All `u32` newtypes. | The owning definition's single `next_local` counter, shared by all its local ID kinds | Definition lineage, stable across revisions. Unique across all kinds within one definition. |
| Project objects | `Id` (instances, symbol occurrences, wires, tracks) | `Project::allocate` | Project |
| Nets | `Id` | `Project::allocate_net` (unchanged) | Project |

`DefinitionId` is an opaque newtype, which provides the library-folder seam. Shared local library folders will need collision-free identities across projects. That work can then change the representation behind the newtype without changing any consumer. Collision-free identity is not part of these slices (see [open questions](#open-questions-and-deferrals)).

`FunctionId` is unique per component lineage, not per terminal. A `FunctionKey { terminal, function }` is therefore redundant by design: publication and selection both validate that the function belongs to the named terminal, so a key can never pair a terminal with another terminal's function.

**Local IDs never reuse a retired value.** Every definition with local IDs carries `next_local: u32`. Publishing a revision fails when:

- Any local ID in the revision, of any kind, is not below that revision's own `next_local`.
- An ID absent from the base revision is below the base's `next_local`. That would be a deleted ID reused with a possibly different meaning, which [the spec forbids disguising](part-library-design.md#updates-must-explain-what-changes).
- `next_local` is lower than the base's.

The first rule closes the gap the other two leave: without it, r2 could publish ID 10 with `next_local` 5, r3 could remove 10, and r4 could re-add 10 with a new meaning while passing the base check.

The illustrative JSON in the spec uses string IDs (`"io-a"`, `"gpio-in"`). These slices use typed numeric local IDs with separate labels, consistent with existing `Endpoint`, net and pad identities. Labels are display text and never identity.

### Reference graph (acyclic)

```text
ComponentInstance ──pins──▶ ComponentRef ──pins──▶ SymbolRef*        (allowed representations)
      │                          │        ├─pins──▶ BindingRef*       (allowed implementations)
      │                          │        └─pins──▶ FieldRef*         (slice 2, selected fields)
      │ chooses (lineage IDs,    │
      │ resolved through the     BindingRef ──pins──▶ PackageRef
      │ pinned component)        │          ├─pins──▶ FootprintRef*   (allowed footprint variants)
      │                          │          └─owner─▶ component DefinitionId (lineage, not revision)
      ▼                          FootprintRef ──pins──▶ PackageRef (must equal the binding's)
  representation: symbol         SymbolRef ──owner──▶ component DefinitionId (lineage)
  physical: { binding, footprint } FieldRef ──pins──▶ QuantityKindRef (slice 2, quantity/tolerance/range types)
```

| Pinner | Pins exactly | Records lineage only | Never pins |
| --- | --- | --- | --- |
| Component revision | Allowed representations (`Vec<SymbolRef>`, at most one per symbol lineage); allowed implementations (`Vec<BindingRef>`, at most one per binding lineage); slice 2: selected fields (`Vec<FieldSelection { field: FieldRef, … }>`, at most one per field lineage) | — | Packages or footprints directly |
| Symbol revision | — | Owning component lineage, so its pins' terminal IDs are interpreted in that component's namespace | Component revision |
| Binding revision | `package: PackageRef`; allowed footprints `Vec<FootprintRef>`, at most one per footprint lineage, each pinning the same `PackageRef` | Owning component lineage. A binding can be listed only by revisions of that component, so a package shared by two components never shares bindings. | Component revision |
| Footprint revision | `package: PackageRef` | — | — |
| Package revision | — (native model assets are deferred; the envelope stays inline) | — | — |
| Field revision (slice 2) | `QuantityKindRef` where its value type needs one | — | — |
| Component instance | `component: ComponentRef` | `representation: DefinitionId` (a symbol listed by the pinned component); `physical: Option<PhysicalChoice { binding: DefinitionId, footprint: DefinitionId }>` (a binding listed by the pinned component and a footprint listed by that binding) | Anything not reachable through its component revision |
| Symbol occurrence | `instance: Id`, `unit: UnitId` of the instance's resolved representation | — | Its own electrical terminals |

The instance stores one exact pin, its component revision. Its choices are lineage IDs. `instances::resolve(&Library, &ComponentInstance)` turns them into exact revisions by walking the graph above. The per-lineage uniqueness rules in the table are publish rules, so each lineage choice has at most one candidate. There is exactly one source of truth for which exact symbol, binding, footprint and package an instance uses, so no redundant exact references can disagree.

Symbols and bindings are owned by one component lineage, so a symbol is not reused across components in these slices. This narrows the spec's "reuse an existing symbol where suitable" deliberately (see [open questions](#open-questions-and-deferrals)).

**Spec ambiguity resolved: direction of the binding pin.** The domain table says a binding names "exact component/package revisions", but a component must also pin which bindings it allows. Pinning in both directions would form a cycle. These slices choose this direction:

- A component revision pins its allowed bindings.
- A binding pins its package and allowed footprints, and records only its component lineage.

This makes "which physical implementations this component revision allows" a property of the pinned component revision. It also gives staged completion for free: a revision with no implementations is schematic-usable and not board-placeable. A binding still cannot float between components, because it is owned by one lineage. The component publication check also requires the mapping to cover that revision's terminals exactly.

The cost is a **revision cascade**. A new footprint revision is adopted through a new binding revision, which is adopted through a new component revision. One `library.publish` set publishes the cascade atomically. Instances then adopt it through one reviewed component-revision update. CE-01 ("publish a new footprint revision and update only R1") becomes: publish {footprint r2, binding r2, component r2}, then update R1 to component r2. R2 keeps component r1 and every choice that it pins.

### Project library snapshot

`Project.library: Library` holds every published revision of every kind: `components`, `symbols`, `packages`, `footprints`, `bindings` and, from slice 2, `quantity_kinds` and `fields`. Each is a `Vec<Published<T>>` with `Published<T> { id, revision, meta: DefinitionMeta, definition: T }`. `DefinitionMeta { name, description, provenance }` is the envelope common to every kind and is owned by `library`; definition bodies carry no metadata of their own.

Revisions are immutable. Publishing appends and never rewrites. The snapshot is the transitive closure by construction: document validation requires every exact reference in every published revision, and every instance pin, to resolve to a stored revision of the correct kind. A project therefore reopens offline with no other source. Unreferenced old revisions stay in the snapshot. A `library.prune` command is proposed later, not part of these slices.

### What a library update changes

- `library.publish` changes only the library. Instances, occurrences, wires, nets, placements and tracks are untouched, and existing instances keep their pins.
- An instance changes revision only through `project.preview_update` / `project.apply_update` with `Change::ComponentRevision { instances, target: ComponentRef, resolutions }`. The target must have the same component lineage. The plan diffs everything reachable from the old and new pins:
  - Units and pins (slice 1); graphics by ID, pin presentation and pin text height ([G1a](#drawable-symbol-graphics-g1a)).
  - Binding mapping, footprint pads, datum and package envelope (slice 1, as today's part-revision plan).
  - Field schemas, defaults and effective values (slice 2).
  - Terminal functions and selections (slice 3).
- A plan is **blocked** when an instance's current choice is not offered by the target, until `resolutions` supplies an explicit replacement. Examples: its representation, binding or footprint lineage is no longer listed; an occurrence's unit no longer exists in the same symbol lineage; an override no longer fits; a selected function is gone. Nothing is inferred from names, order or pad count.
- **Unit IDs are lineage-local.** Unit 2 of symbol X and unit 2 of symbol Y are unrelated. When a `ChoiceResolution` changes the representation lineage, the plan is blocked until every occurrence and every `unused_units` entry of that instance has an explicit `UnitResolution`. A unit is never kept by numeric match across lineages.
- Within one symbol lineage, a unit ID keeps its meaning. A target revision that removes a unit with an occurrence blocks until a `UnitResolution` is given. A target that removes a unit listed in `unused_units` lists that flag's removal in the plan; it does not block, because no presentation or connectivity is lost.
- **Regrouping never disconnects silently.** When a terminal's pin moves to another unit and the terminal is wired, the plan is blocked unless the target unit is placed. A `RegroupResolution` either places the target unit at a given position or explicitly accepts disconnecting the listed wires. There is no default.
- Cancel means not applying, so the old pins remain. Apply is one undo step. A stale plan fails without changes, as today.

## (b) Incomplete drafts and completeness

### One type, optional parts

Drafts and published revisions use **the same definition types**. A draft may have:

- Empty or partial collections: no terminals, no units, a binding without mappings.
- Empty names.
- Duplicate local IDs.
- References to revisions that do not exist yet.

Only persistence bounds and finite geometry are enforced on a draft (`library::check_bounds`). A NaN or out-of-range coordinate is rejected even in a draft, because it cannot be persisted meaningfully. A structurally contradictory but finite draft is kept as visible draft input.

`Document` becomes `{ project: Arc<Project>, drafts: Arc<Drafts> }`. `Drafts { items: Vec<Draft> }` stores `Draft { id: DefinitionId, base: Option<Revision>, meta: DefinitionMeta, definition: Definition }`. There is at most one draft per lineage. `Definition` is the kind-tagged enum over the definition bodies. A draft's pending revision is `base + 1`, or `1` when it has no base.

Drafts stay outside `Project`, as `authoring_draft` does today. Draft edits therefore neither revalidate the project nor invalidate the board scene key. Undo history covers both halves.

Creating a new lineage draft is the one draft operation that touches the project: it reserves a `DefinitionId` from `Project::allocate`. That keeps a single identity allocator and lets drafts reference each other's pending revisions as ordinary exact references before anything is published.

### Persistence and recovery

`EditorFile { version: 1, project: Project, drafts: Drafts }` replaces `authoring_draft: Option<Part>`. Saving and recovery are unchanged in `pcbcraft-io`, which serializes `EditorFile` atomically and in bounded form. Drafts therefore survive save, crash recovery and offline reopen exactly as written, including unfinished content.

Decode validates the project fully. For drafts it checks only bounds, kind and identity consistency (lineage allocated, kind consistent with any published revisions of the same lineage, base revision exists).

### Derived completeness, no stored stamp

No definition or instance stores a "valid", "verified" or "complete" flag. Completeness is computed on demand from findings. `Finding` gains `blocks: Option<Stage>` and the predicate `Finding::blocks_stage(Stage) -> bool`:

```rust
pub enum Stage { Publish, BoardPlaceable, ElectricallyResolved }
```

A state holds when no current finding blocks it. Purchasing resolution is not computed in these slices: there is no manufacturer-part model yet, and reports say so explicitly. Manufacturing readiness is out of scope. These are the states from the spec:

| Spec state | Derived as | Checked by |
| --- | --- | --- |
| Recoverable draft | Any draft passing `check_bounds` | `library::check_bounds` |
| Schematic-usable definition | A published component revision. Publishing it requires no `Stage::Publish` findings for that component and its representations. | `library::publish_findings` |
| Board-placeable instance | No `BoardPlaceable` findings: physical choice present and resolvable, binding/footprint complete for the pinned component | `completeness::instance` |
| Electrically resolved instance | No `ElectricallyResolved` findings: every unit placed or marked unused; every electrical terminal accounted for (`nets::accounted_for`); no required power input marked no-connect; (slice 2) required fields supplied; (slice 3) every function resolved and resource requirements satisfied | `completeness::instance` |

Function availability in the chosen binding is **not** a finding. It is an invariant (`instances::check_instance`): a state that violates it is rejected by direct commands and blocks plans, so it can never be observed. ERC findings (`erc.*`) and board findings (`board.*`) have `blocks: None`. They describe circuit and board state, not component completeness, as the spec requires.

### What `library.publish` validates

`library.publish { drafts }` takes 1–32 draft IDs. It publishes them as one transaction in dependency order: quantity kinds, then fields, packages, footprints, bindings, symbols and finally components. A reference may point to an existing revision or to another draft's pending revision in the same set. The command fails with `conflict` and publishes nothing if any of these hold:

- Any finding satisfies `blocks_stage(Stage::Publish)`.
- A base is not the latest revision (stale draft).
- A pending reference cannot be satisfied.

Afterwards, each published draft becomes a draft of its new revision, ready for the next edit, as `part.publish` behaves today.

Publish rules per kind are owned by `library::publish_findings` and use domain validators from `fields` and `functions`. Document decode validates every published revision with **the same** function and rejects it on exactly the findings that satisfy `blocks_stage(Stage::Publish)`, the predicate `library.publish` uses. Advisory publish findings (`blocks: None`) never make a saved file fail to reopen. No rule is written twice.

- **Every kind with local IDs:** the [local-ID rules](#identity).
- **Component:**
  - 1–256 terminals with unique nonzero IDs and printable names.
  - ≥ 1 representation, at most one per symbol lineage. Each listed symbol has the same owner lineage and gives every terminal exactly one pin (`component.pin_missing`, `component.pin_unknown`); every `Field` text it shows is a field the component selects (`component.text_field_unknown`).
  - Implementations at most one per binding lineage. Each listed binding has the same owner lineage, maps every terminal to at least one package terminal and maps no unknown terminal.
  - Slice 2: field selections are unique per field lineage, and defaults satisfy their field.
  - Slice 3: function declarations are valid (`functions::declaration_findings`); every `FunctionKey` in constraints and in listed bindings' `unavailable` names a function of its own terminal; the default resolution (fixed functions and design defaults, no explicit selections) has no conflicts under the component's capacity and `Excludes` constraints; no listed binding marks a fixed function or a design default unavailable (`functions::binding_findings`).
- **Symbol:** 1–64 units with unique IDs and labels; pins with unique terminals across all units (`symbol.pin_duplicate`); every unit draws something or has a pin (`symbol.unit_empty`); finite geometry within the [graphics bounds](#drawable-symbol-graphics-g1a); each graphic passes the `graphic.*`, `text.empty` and `text.too_long` rules.
- **Package:** 1–512 terminals with unique IDs and unique printable designations; positive finite envelope.
- **Footprint:** 1–1024 pads with unique IDs and a valid shape; SMD and plated-through pads land a package terminal and non-plated holes and fiducials never do; every landed terminal exists in the pinned package; every package terminal has ≥ 1 pad; holes, pad vias and paste windows lie inside their land; drawings, polarity and the stored source are consistent; finite datum. The full list is in [footprint data and rules](#footprint-data-and-rules-f1-core).
- **Binding:**
  - Every package terminal of the pinned package maps to exactly one electrical terminal, and no unknown package terminal is mapped.
  - 1–16 footprints, at most one per footprint lineage, each pinning the same package revision.
  - Slice 3: `unavailable` keys are unique. Whether they name real functions is checked by the owning component's publication, which has the declarations.
- **Field and quantity kind (slice 2):** see [slice 2](#slice-2--typed-fields-and-quantities).

The slice 3 default-resolution rule guarantees that `component.place` with no explicit selections, and any physical choice the component lists, starts in a conflict-free state. A component that could never be placed is rejected at publication.

A component may be published with **no implementations**. Packages, footprints and bindings may be published independently once their own dependencies validate. Publication never stamps verification. `provenance` remains free text, separate from structural validity.

## (c) Generator and override seam (deferred to CE-03)

These slices only keep the seam open. They do not implement recipes, generation keys or overrides.

- **Persistent IDs are separate from generation keys.** `PadId` (and later other generated object IDs) are persistent local IDs from `next_local`. A future generator returns objects keyed by a recipe-defined `GenerationKey` (string, bounded). It never returns `PadId`s.
- **Where the mapping lives.** A future `GeneratorRecipe` definition kind (`Definition::Recipe`, with its own revisions and pinned source/API/input fields) is pinned by the footprint revision it produced. The footprint revision then carries `generated: Option<GeneratedFootprint { recipe: RecipeRef, keys: Vec<(GenerationKey, PadId)>, overrides: Vec<PadOverride { pad: PadId, property, value }> }>` inside `library::footprint`. The mapping and overrides are part of the immutable revision that the snapshot preserves. Neither is instance state.
- **What these slices do.** `part.generate_pads` is renamed `library.generate_pads { draft, script }`. It operates on a footprint draft with the existing proof semantics: it emits each existing `PadId` exactly once, preserves package-terminal associations and allocates nothing. It does not persist script source or create a recipe.

## (d) Module map

### Core modules (`crates/editor-core/src`)

Each row is one cohesive concern with a narrow public surface. "May use" is the complete allowed set of `crate::` imports, including names reached through crate-root re-exports. `cargo xtask core-modules` (part of `cargo xtask ci`) enforces this table; change the table in `xtask/src/core_modules.rs` and here together. The list is acyclic: a module uses only modules with a lower number. Two consequences are deliberate:

- **Data before rules.** `model` holds the project aggregate, including instance and occurrence data, with no rules. The rule modules above it (`instances`, `nets`, `schematic`, `layout`) take `&Project`, so a rule that needs whole-project state has an owner below `validate`, `updates` and `commands`.
- **Payloads live where they execute.** A command payload type lives in the lowest module that can execute it. `SchematicCommand` and `LayoutCommand` stay in `schematic` and `layout` with an `apply(&mut Project, command, EditPolicy)` that holds their rules, as today. The project carries its library snapshot, so rule functions that take `&Project` need no separate `&Library`. `LibraryCommand` and `InstanceCommand` span several domain modules, so they live in `commands`, which only dispatches. `updates` never names a `commands` type.

Command handlers in `commands` orchestrate: they look up, clone a candidate, call domain functions and commit. They hold no domain rules. `Engine::apply` ends every candidate with `nets::reconcile` and `validate::edited`, which is `validate::project` except that the library snapshot is revalidated only when it changed.

`updates::stage(&mut Project, &InstanceChange, EditPolicy)` is the single composition of consequential instance edits. `InstanceChange::Remove` runs `schematic::detach_instance`, `layout::detach_instance` and `instances::remove` in that order; `InstanceChange::SetPhysical` runs `layout::set_physical`. `commands` serves `component.remove` and `instance.set_physical` by calling `updates::stage` with `EditPolicy::Direct`; `project.apply_update` calls it with `EditPolicy::Consequential`. The guard and the composition are therefore written once.

Notes on the boundaries:

- `quantity` knows nothing about Rhai. `scripting` registers `quantity::Quantity` operations and keeps its `Script`/`Input` types and pad-specific `millimetres` conversion. Rhai values never leave `scripting`.
- `fields` owns value meaning: parsing, checking, defaults versus overrides and formatting. `library` stores field definitions but calls `fields` to check them. `instances` calls `fields` to check and resolve `InstanceFields`.
- `functions` owns function meaning and the single `resolve` algorithm. Its inputs are plain `functions` types; it never sees `library` or `model` types. `instances::function_resolution(&Library, &ComponentInstance)` is the one place that builds those inputs from the pinned component and chosen binding. Three modules consume the output, each for a different purpose:
  - `instances::check_instance` rejects structural selection errors and the `conflicts` bucket.
  - `completeness` reports the `unresolved` and `incomplete` buckets as findings.
  - `erc` applies drive rules to the `active` bucket.

  Each rule is implemented once, in `functions`.
- `nets`, `erc` and `completeness` read terminal and component declarations directly through `library`, which their "may use" sets list. They read definitions only through the exact references that `instances::resolve` returns.
- `model` is an aggregate with no rules; its public functions are lookups. `EditPolicy { Direct, Consequential }` lives there because `schematic`, `layout` and `updates` share it.
- `parts.rs` is deleted; its rules move to `library::publish` and its templates to `library::samples`. `schematic::checks` moves to `erc`.
- Intra-crate module dependencies are not enforced by `cargo xtask layers`. This table is the reviewed contract (see [open questions](#open-questions-and-deferrals)).

## (e) Command families

All mutations are `Operation` variants: `Library(LibraryCommand)`, `Instance(InstanceCommand)`, `Schematic(SchematicCommand)`, `Layout(LayoutCommand)` and `Update(Box<ApplyUpdate>)`. `Operation::Part` is removed. `Engine::apply` returns `Result<Outcome>`, where `Outcome` is one of:

- `None`
- `DraftCreated { id }`
- `Published { revisions: Vec<DefinitionRef> }`
- `InstancePlaced { instance, occurrence }`
- `UnitPlaced { occurrence }`
- `PropertiesSet { effective: Vec<EffectiveField> }` (slice 2)
- `FunctionsSelected { resolution: functions::Resolution }` (slice 3)
- `GridSet { off_grid: Vec<OffGridPin> }` (G1a)

Every successful mutation is one undo step.

Read-only reports are `Query` variants answered by `Engine::query(&self, Query) -> Result<QueryResult>`: `Query::InspectInstance { instance }` returns `completeness::InstanceReport`, `Query::CheckDefinition { target: CheckTarget }` returns `completeness::DefinitionReport` and `Query::CheckDrafts {}` returns one `DefinitionReport` per draft, in draft order, from a single staging. Queries never create undo entries or change the revision. CLI, MCP and the desktop call `Engine::query` and present its result unchanged.

Where the code had to settle something this contract left open, it chose the option that keeps concerns separate. These choices are now part of the contract:

- **Draft checks.** `component.check` on a draft evaluates its pending revision against the snapshot plus every other current draft's pending revision, so references inside a publish set resolve as they would on publish. `library::candidate` stages them, the same staging `library.publish` uses. - **Error codes.** Blocking findings make `library.publish` fail with `conflict` and document decode fail with `invalid_input`. `library.draft_from` accepts any stored revision as the base; publishing a non-latest base is the stale `conflict`.
- **One-pass validation.** `instances::check_all` runs `check_instance`'s single rule body for every instance with one pass over occurrences and wires; `validate::project` calls it instead of looping `check_instance`.
- **Routed-net protection.** `Engine::apply` calls `schematic::protect_routed_nets` after `nets::reconcile` for every operation except `Update`; reviewed updates list affected copper instead.
- **`layout::apply` takes no `EditPolicy`.** Layout commands have no consequential form; the consequential layout edits are `layout::set_physical` and `layout::detach_instance`, called by `updates::stage`.
- **Payload types.** `component.place` carries `instances::NewInstance`. `Query` is tagged `query`/`params` with the command names `component.inspect`/`component.check`; `QueryResult` is tagged `report`/`result`; `CheckTarget` is tagged `target`/`id`. `UnitTarget` serializes as `{"unit": n}` or `"drop"`. In `ChoiceResolution`, an absent `physical` keeps the current choice, `null` clears it and a value replaces it.
- **Resolution checks.** A resolution naming an instance outside the update, or a `UnitResolution` for a unit with neither an occurrence nor an unused flag, is `invalid_input`. - **Samples.** `library::samples` has `two_terminal` and `two_terminal_header` (the desktop's Connector template). Both take `SampleRefs`, the lineages and the revisions they pin of each other; neither is a category.

## Slice 2 — typed fields and quantities

**Quantity module.** Move `scripting/quantity.rs` to `crate::quantity` and make its checked operations public. `scripting` imports it, and the reverse import is forbidden.

**One unit type.** `UnitOfMeasure { symbol, aliases: Vec<String>, scale: f64, si_prefixes: bool }` replaces `UnitDefinition { symbol, dimension, scale }`. A unit carries no dimension of its own. `UnitSet { dimension: Dimension, units: Vec<UnitOfMeasure> }` supplies it for a group of units, and `UnitSet::to_si(value, symbol)` is the single scaling rule. `fields::QuantityKind` embeds one `UnitSet`. `scripting::Script.units` becomes `Vec<UnitSet>`, and `scripting::Input::Quantity { value, unit }` is scaled through `UnitSet::to_si`; a unit symbol must be unique across a script's sets. The scripting proof and field parsing therefore share one type and one rule.

`parse(text, &UnitSet, default_unit)` follows these rules:

- **Grammar:** `number [whitespace] [suffix]`, where `number` is a decimal with optional sign and exponent and `.` as the separator.
- **Suffix resolution, first match wins:**
  1. The suffix is a unit symbol or alias.
  2. The suffix is an SI prefix followed by a prefix-accepting unit symbol.
  3. The suffix is a bare SI prefix applied to the default unit.
  4. There is no suffix, so the default unit applies.
- **Examples:** with a resistance kind whose default unit is `Ω`, `10k`, `10 kΩ` and `10000 Ω` all parse to SI value 10000. `10m` gives 0.01 Ω. Rule 1 would make it 10 m for a length kind with unit `m`.
- **Prefix table:** the SI prefixes from p to G, including `µ` and the ASCII alias `u`.
- **Rejections:** any other suffix, such as `µF` for resistance, is rejected as `invalid_input` naming the unit and kind. Non-finite results or results beyond the existing ±1e100 bound are rejected too.
- **Deferred:** RKM notation such as `4k7`, affine units and logarithmic units.

**Field data** (`fields` bodies, stored as library definitions with `DefinitionMeta` in the library envelope):

- `QuantityKind { units: UnitSet, default_unit }` is a definition with identity. Two kinds with the same dimension are different kinds. A unit symbol never establishes kind identity.
- `FieldDefinition { value_type: ValueType, default: Option<FieldValue>, required_at: Option<Stage> }`, where `ValueType` is one of:
  - `Quantity { kind: QuantityKindRef, min: Option<f64>, max: Option<f64> }` (SI)
  - `Integer { min: i64, max: i64 }`
  - `Boolean`
  - `Enum { choices: Vec<Choice { id: ChoiceId, label }> }`
  - `Text { max_bytes: u16 }` (≤ 256)
  - `Tolerance { basis: Relative | Absolute { kind: QuantityKindRef } }`
  - `Range { kind: QuantityKindRef }`
- `FieldValue` is one of:
  - `Quantity { si: f64, display_unit: Option<String> }`
  - `Integer(i64)`
  - `Boolean(bool)`
  - `Enum(ChoiceId)`
  - `Text(String)`
  - `Tolerance { minus: f64, plus: f64 }` (fractions for relative: `5%` is 0.05 with percent semantics; SI for absolute)
  - `Range { min: f64, max: f64 }`

  `display_unit` is presentation and never changes `si`.
- `ComponentDefinition.fields: Vec<FieldSelection { field: FieldRef, default: Option<FieldValue>, show_on_symbol: bool }>`. The component default overrides the field default and must satisfy the field's constraints.
- `ComponentInstance.properties: InstanceFields` replaces `value`. It is a `BTreeMap<DefinitionId (field lineage), FieldOverride::{Assigned(FieldValue), Unset}>`. A missing key means inherited.
- `fields::effective` returns `EffectiveField { field, value: Option<FieldValue>, origin: Assigned | ComponentDefault | FieldDefault | ExplicitlyUnset | NoValue }`. Assigned zero is a value and is distinct from `ExplicitlyUnset`.
- A required field with no value produces a finding blocking its `required_at` stage.
- Overrides are keyed by field lineage, so a field revision that only renames its label (`DefinitionMeta.name`) keeps every assignment.

**Updates.** In a component-revision plan, a field-revision change reports effective-value changes per instance. If a field kind changes, constraints narrow so an override no longer fits, or a populated field is removed, the plan is blocked until a `FieldResolution` is supplied. Valid overrides are preserved.

**Deferred.** These are not part of slice 2:

- **Derived fields (CE-03).** The seam is a future `derivation: Option<Derivation { expression, inputs: Vec<FieldRef> }>` on `FieldDefinition`, independent of the value type, evaluated by `scripting::evaluate_quantity` with an explicit dependency graph and cycle detection. No such field exists yet, and `Origin::Calculated` is not emitted.
- Structured reference fields.
- Requirement comparison semantics and manufacturer specifications (CE-01, CE-02).

### Slice 2 implementation notes

Where the code had to settle something this contract left open, it chose the option that keeps concerns separate. These choices are now part of the contract:

- **Checked operation names.** The quantity operations are `Quantity::{checked_add, checked_sub, checked_mul, checked_div}`. Strict Clippy rejects inherent `add`/`sub`/`mul`/`div` methods that mimic the operator traits; the fallible operations follow the standard library's `checked_*` naming. Fields are private, so every value is constructed through `Quantity::new`.
- **One resolution rule.** `UnitSet::resolve(text)` applies parse rules 1 and 2 (an exact symbol or alias, then an SI prefix on the symbol or an alias of a prefix-accepting unit) and returns the factor and canonical spelling; `UnitSet::to_si` and `parse` both use it, and `parse` adds rules 3 and 4. A recorded `display_unit` is the canonical spelling (`10kohm` records `kΩ`; a bare `10k` records `kΩ`; no suffix records none). `UnitSet::check` is the one validity rule for a unit set: 1–32 units, at most 8 aliases each, scales within 1e-30–1e30, unique texts and a dimension within ±16. Unit texts that the grammar could not recognise after a number (empty, whitespace or control characters, `/`, `..`, a leading digit, sign or `.`, or an exponent-like `e3`) are rejected.
- **Prefixes.** The table is p, n, µ (with `u` and Greek `μ` accepted as spellings), m, c, d, da, h, k, M and G. Formatting without a recorded display unit uses the engineering subset p–G. Quantity text is limited to 128 bytes and property text to 256 bytes before parsing (`limit_exceeded`).
- **Text forms of other types.** Booleans accept true/false/yes/no; enumerations accept a choice label, case-insensitively; tolerances accept `±5%`, `+/-5%`, `5%` or `-20%/+80%` (also with U+2212 and `ppm`) for relative, and quantities of the named kind for absolute; ranges accept `min .. max`. `fields::display` formats values in a form `parse_value` reads back.
- **`FieldDefinition.next_local`.** Enumeration choice IDs are local IDs, so field definitions carry `next_local` and follow the [local-ID rules](#identity). Quantity kinds have no local IDs. `Choice { id, label }` and `ToleranceBasis::{Relative, Absolute { kind }}` are the named forms of the contract's choices and tolerance basis.
- **Publish order and findings.** Quantity kinds and fields come first in a publish set. Their findings are `quantity_kind.units`, `quantity_kind.default_unit` (the default unit must be a unit symbol), `field.value_type`, `field.choice_label`, `field.default_invalid`, `field.required_stage` (`required_at` may not be `Publish`) and `reference.missing`; components add `component.duplicate_field_lineage` and `component.field_default_invalid`. `fields::definition_findings` and `fields::kind_findings` own these rules; `library::publish_findings` resolves the kind and aggregates them, so decode and publication apply the same rules.
- **Effective fields carry presentation.** `EffectiveField { field: FieldRef, label, value, origin, text, show_on_symbol, required_at }`: the exact field revision selected by the pinned component, the field name, the formatted text and the selection's display flag, so transports and the desktop present values without reformatting. `component.inspect` reports them as `InstanceReport.properties`. A required field without a value is finding `instance.field_required` on `ObjectRef::Property { instance, field }`, blocking its `required_at` stage.
- **Rule owners.** `fields::apply_input` applies one `PropertyInput`; `instances::set_properties` and `component.place` (`NewInstance.properties`, default empty) look up the selected field and kind and call it for each edit, failing the batch on the first invalid edit with a message naming the instance, field and quantity kind. `instances::check_instance` checks every override: its field lineage is selected by the pinned component and an assigned value satisfies that field revision. `Library::field_view` resolves a field revision with its kind.
- **Updates.** `instances::carry_properties` owns the update rule. An assigned value blocks when the target no longer selects its field, when the value type or quantity-kind lineage changes (`fields::compatible`), or when it no longer satisfies the target field. An explicit `Unset` on a removed field is dropped and listed. A supplied `FieldResolution` is applied as a property edit against the target field even when none is needed, and must itself be valid; `Inherit` also resolves a removed field. Plans report effective-value changes and field renames per instance (`R1: field ‘Count’ 8 (Assigned) → 5 (Assigned).`).
- **Demo data.** `library::samples::resistance_field` supplies a resistance quantity kind (Ω with aliases `ohm` and `R`) and a non-negative quantity field; `Engine::demo` selects it on the sample component with `show_on_symbol` and places R1 and R2 with `10k`.
- **Desktop.** The schematic inspector edits the fields marked `show_on_symbol` as text through one `instance.set_properties` batch; an emptied box sends `Inherit`. It shows the rejection message from `fields::parse_value` while typing; the engine still decides on apply and its error appears in the status line. Symbols and the sheet list show the effective texts. Fields are not yet authored in the component editor; drafts of fields and kinds are edited through `library.edit`.

## Slice 3 — terminal functions and selections

**Declaration** (`functions` types, stored in `library::component`):

- `Terminal { id, name, class: TerminalClass }` replaces `kind: PinKind`. `TerminalClass` is one of:
  - `Electrical(functions::TerminalFunctions)`, where `TerminalFunctions { functions: Vec<Function>, design_default: Option<FunctionId> }` (1–32 functions) is the one declaration type owned by `functions`
  - `DeviceNc`
  - `Reserved`
- `Function { id: FunctionId, label, direction, signal: SignalKind, drive: Drive, resource_role: Option<ResourceRole { resource, role }> }`, with:
  - `Direction` = `Input` | `Output` | `Bidirectional` | `Passive` | `PowerInput` | `PowerOutput`
  - `SignalKind` = `Digital` | `Analog` | `Power` | `Unspecified`
  - `Drive` = `None` | `PushPull` | `OpenDrain` | `OpenSource`
- **Valid combinations:**
  - `Input`, `Passive`, `PowerInput` and `PowerOutput` require `Drive::None`.
  - `Output` and `Bidirectional` require a drive other than `None`.
  - `SignalKind::Power` is valid only with the two power directions, and the power directions require it.
  - Other combinations are rejected at publication.
- **Resource rules:** `ComponentDefinition.resources: Vec<Resource { id, label, roles: Vec<Role { id, label, capacity: u16, required_when_used: bool }> }>` and `constraints: Vec<FunctionConstraint::{Excludes { a: FunctionKey, b: FunctionKey }, Requires { selected: FunctionKey, requires: FunctionKey }}>`. Constraints are scoped to one instance.
- `BindingDefinition.unavailable: Vec<FunctionKey>` declares functions that are unavailable in that implementation.
- **Device NC versus project no-connect:**
  - `DeviceNc` and `Reserved` are definition classifications. They have no functions, cannot be wired and cannot take a project no-connect marker, which would be redundant.
  - `ComponentInstance.no_connect` is a project decision on an `Electrical` terminal.

**Selection and resolution.** `ComponentInstance.functions: FunctionSelections` maps `TerminalId` to `FunctionId`. The resolver's whole input is plain `functions` data:

```rust
pub struct TerminalDeclaration<'a> {
    pub terminal: TerminalId,
    pub functions: Option<&'a TerminalFunctions>, // None for DeviceNc and Reserved
}

pub fn resolve(
    terminals: &[TerminalDeclaration<'_>],
    resources: &[Resource],
    constraints: &[FunctionConstraint],
    unavailable: Option<&[FunctionKey]>, // None without a physical choice
    selections: &FunctionSelections,
) -> Result<Resolution>;
```

It returns `invalid_input` for structural errors: an unknown terminal, a function that does not belong to its terminal, or a selection on a non-`Electrical` terminal. It decides each terminal's active function in this order:

1. Explicit selection.
2. The only function of a fixed-function terminal.
3. `design_default`. A reset-state description is never a default.
4. Otherwise the terminal is unresolved.

`Resolution` has four buckets:

| Bucket | Contains | Handling |
| --- | --- | --- |
| `active` | The active function per terminal | Used by ERC; returned by `FunctionsSelected` |
| `unresolved` | Terminals with no active function | Finding `config.function_unresolved`, blocking `ElectricallyResolved` |
| `conflicts` | Role capacity exceeded; an `Excludes` pair both active; unavailable in the chosen binding | Invariant: **rejected** by `instances::check_instance`, so by `instance.select_functions` and `set_physical`, and blocked in plans. Never a finding. |
| `incomplete` | A role with `required_when_used` absent while another role of its resource is active; an unmet `Requires` | Finding `config.requirement_unmet`, blocking `ElectricallyResolved` |

Selections are keyed by IDs, so reordering or relabeling functions in a new revision preserves them.

**ERC** (`erc::checks` replaces the `PinKind` rules; findings have `blocks: None`). For each net, the rules use active functions only:

| Code | Condition |
| --- | --- |
| `erc.driver_conflict` | Two or more push-pull or open-source drivers (`Output`/`Bidirectional` with that drive). |
| `erc.open_drain_contention` | At least one push-pull driver together with at least one open-drain driver. |
| `erc.input_only_net` | ≥ 2 terminals, at least one `Input`, and no `Output`, `Bidirectional` or `Passive` terminal. |
| `erc.undriven_power_input` | A `PowerInput` with no `PowerOutput` on its net. Retained from today. |
| `erc.unchecked_terminal` | Emitted for each unresolved terminal on the net. That terminal is excluded from drive rules, so ERC never assumes all alternatives at once and never picks one. |

A terminal alone on its net is not an ERC condition. It is reported once, by `completeness`, as `instance.terminal_unaccounted` through `nets::accounted_for`.

Several open-drain drivers with a passive pull-up produce no finding. This is the observable proof that drive behavior, not direction alone, is used. In completeness, a `PowerInput` function with a project no-connect is `instance.required_terminal_no_connect`, so an obligation cannot be hidden.

### Slice 3 implementation notes

Where the code had to settle something this contract left open, it chose the option that keeps concerns separate. These choices are now part of the contract:

- **Shapes.** `TerminalClass` serializes externally tagged: `{"electrical": {"functions": […], "design_default": n}}`, `"device_nc"` or `"reserved"`, so a device-NC or reserved terminal with functions is not representable and decodes as malformed. `ComponentDefinition` gains `resources` and `constraints`; `BindingDefinition` gains `unavailable`; `ComponentInstance` gains `functions: FunctionSelections` (a map from terminal ID to function ID). `FunctionConstraint` is tagged `excludes`/`requires`.
- **One local-ID namespace.** Terminal, function, resource and role IDs all come from the component's `next_local` and follow the [local-ID rules](#identity). Duplicate function IDs are therefore the existing `definition.local_id_invalid` finding; `functions` does not restate uniqueness.
- **Resolution buckets.** `Resolution { active, unresolved, conflicts, incomplete }`. `ActiveFunction` carries the function's label, direction, signal, drive and `origin` (`ActiveOrigin::{Selected, Fixed, DesignDefault}`), so ERC needs no second lookup. `Conflict::{Capacity, Excluded, Unavailable}` and `Requirement::{RoleMissing, Requires}` carry typed keys and a message. `TerminalFunctions::implicit` is the one fixed-or-default rule, used by `resolve` and by `binding_findings`.
- **Publication findings** (`functions::declaration_findings`, `functions::binding_findings`, aggregated by `library::publish_findings`): `function.count`, `function.label` (unique per terminal), `function.combination`, `function.design_default`, `function.resource_unknown`, `resource.label`, `resource.role_count`, `resource.role_label`, `resource.role_capacity` (≥ 1), `function.constraint_key`, `function.default_conflict`, `binding.unavailable_unknown`, `binding.unavailable_required`; the binding's own `binding.unavailable_duplicate`.
- **Rule owners.** `instances::function_resolution` is the only place that builds `resolve` input. `instances::check_instance` rejects structural selection errors as `invalid_input` and any conflict as `conflict`; `layout::set_physical`, `updates::candidate` and decode therefore reject or block an unavailable function without a separate check. `instances::carry_functions` owns the update rule: a selection is kept when the target still offers that function on that terminal, otherwise the plan is blocked until a `FunctionResolution` names the terminal; resolutions are applied as selection edits and the result is checked once. Plans list function additions, removals, relabels (`U1 terminal 2: function 46 ‘uart-tx-alt’ is relabeled ‘uart-tx-b’; selections are kept by ID.`), behavior changes and selection changes; a reorder alone lists nothing.
- **Completeness.** `config.function_unresolved` names `ObjectRef::Terminal` of each unresolved terminal, including project no-connect terminals; `config.requirement_unmet` names the instance and the terminals whose functions take part. `instance.required_terminal_no_connect` uses the active function's `PowerInput` direction. `InstanceReport.functions` reports the resolution.
- **ERC.** `erc.multiple_outputs` is replaced by `erc.driver_conflict`; power outputs are no longer counted as drivers. `erc.driver_conflict`, `erc.open_drain_contention`, `erc.input_only_net` and `erc.unchecked_terminal` apply to nets with at least two terminals, because a lone terminal is a completeness condition. `erc.undriven_power_input` applies to every net, as before. `erc.unchecked_terminal` names the net and the terminal.
- **Labels.** `ids::printable` and `ids::MAX_LABEL` are the one label rule for `library`, `fields` and `functions`, replacing two private copies.
- **Fixed-function constructor.** `TerminalFunctions::fixed(id, direction)` builds one function with the conventional behavior of a direction (push-pull for driving directions, power signal for power directions). The samples, the desktop and the test fixtures use it; it is data construction, not a category.
- **Samples.** `two_terminal` terminals 1–2 carry fixed passive functions 3–4, so the sample component's `next_local` is 5.
- **Desktop.** The part editor's terminal dropdown offers passive, input, output, power input, power output and device NC. Choosing one replaces the terminal's class with one fixed function, keeping the ID of an existing single function or allocating one from `next_local`. A terminal with several functions shows its function count. Multi-function authoring and selection came later with the Pins tab and the pin-mux panel ([as built](#pin-functions-peripherals-rules-pinout-import-and-firmware-c1c7-as-built)).
- **Boxed report.** `QueryResult::Instance` holds a `Box<InstanceReport>` because the report grew with `functions`; serialization is unchanged.
- **Cleanup tests.** The CE-06 "unrouted ground land" row is asserted: with lands 21 and 22 routed, land 23 of the same terminal and net stays a separate island reported by `board.unrouted`, and routing it clears the finding. Separate tests cover a `Requires` constraint (`config.requirement_unmet` until the prerequisite is active, with undo/redo) and `erc.undriven_power_input` (a lone power input, two power inputs, then a power output on the net).

**Deferred.** These are not part of slice 3:

- Availability restricted by configuration fields.
- Simultaneous multi-mode hardware (reported as unsupported if declared).
- MPN availability checks.
- The pin-configuration table UI.
- Firmware generation.

## Designator prefix and package form

Two authored values that other parts of the editor used to guess from names:

- **`ComponentDefinition.designator_prefix`**: 1–8 uppercase ASCII letters (`R`, `C`, `L`, `D`, `Q`, `U`, `J`, `TP`, …). Anything else is the blocking `component.designator_prefix` finding at publication; the Component panel uppercases letters as they are typed and shows the invalid look otherwise. `component.place` without a designator numbers the instance `{prefix}{n}` with the lowest n ≥ 1 that no designator in the project takes case-insensitively (`R03` and `R2A` do not take a number). Explicit designators keep the existing rules. The prefix is a label rule, not electrical meaning: nothing infers compatibility or behaviour from it.
- **Package form, envelope, model and placement (M1).** `PackageDefinition { next_local, terminals, form, envelope, model, placement }` replaced `body_size`, `model_offset` and `body: PackageBody`. `form: PackageForm` is the typed physical construction (`generic`, `chip` with `kind: resistor | capacitor | inductor`, `gull_wing`, `no_lead`, `header`; `library/package_form.rs`) and the only source of `pkg_*` values. `envelope` is length, width and height from the seating plane up, centred in x and y; a typed form derives it (`PackageForm::envelope`, set by `PackageEdit::SetForm`), a generic package authors it. `model: PackageModel` is `envelope { material }`, `generated { family_rev, materials }` (per-`BodyRole` overrides of the family default materials) or `imported` (M4 placeholder). `placement: ModelPlacement { translation, rotation_deg }` puts the model in the datum frame, rotated intrinsic X → Y → Z in degrees, exact at quarter turns. The 3D view reads only these values (`appearance::Body::of` reads `chip_kind`), so a capacitor renamed R7 still renders as a capacitor.
- **Frames.** `model_frame(&Datum, &ModelPlacement)` is M = D ∘ placement; `FootprintDefinition::envelope_outline` projects the envelope box's corners through it, so the part editor, PCB 2D, the courtyard template and the evaluator see the datum, the placement shift and any quarter turn (a model stood up shows its height across). A generated model's occurrence is jointed at `model_frame`; an envelope body still takes only the placement's translation.
- **Lead order.** `PackageForm::lead_points` (the one lead order: the generated models number their lead bodies and `package_fit` pairs leads with pads by it) gives each lead's seating-plane contact in the model frame, counter-clockwise from above starting at the −x end of the −y row (two rows: −y left to right, then +y right to left; four sides continue +x upward, +y, −x downward); a no-lead exposed pad comes last; a chip's terminal 1 is at −x; header pins run column by column from −x with row 0 at −y. Leads match package terminals by position.
- **`pkg_*` values.** Always `pkg_L`, `pkg_W`, `pkg_H` (the envelope) and `pkg_n` (terminal count). Chip: `pkg_T` (height), `pkg_a` (termination). Gull-wing: `pkg_e`, `pkg_nx`, `pkg_ny` (leads on each ±y and ±x side), `pkg_E1` (body width), `pkg_E` (span across y), `pkg_A1` (standoff), `pkg_A2` (body height), `pkg_b`, `pkg_c` (lead width, thickness), `pkg_Lf` (foot), and `pkg_D` (body length) for two sides or `pkg_D1` (body length) and `pkg_D` (span across x) for four. No-lead: `pkg_e`, `pkg_nx`, `pkg_ny`, `pkg_D`, `pkg_E`, `pkg_A`, `pkg_b`, `pkg_Lt` (terminal length) and `pkg_D2`, `pkg_E2` with an exposed pad. Header: `pkg_e`, `pkg_rows`, `pkg_per_row`, `pkg_row_pitch`, `pkg_body_h`, `pkg_pin`, `pkg_pin_above`, `pkg_pin_below`.
- **Findings and bounds.** More than 512 leads, or more than 16 role materials, is a refusal (`check_bounds`); non-finite placement or form values are refused with the other geometry. Blocking publish findings: `package.form_range` (each violated range or consistency rule: lengths 0.01–1000 mm, terminations leaving body between them, leads fitting their edge without touching, spans reaching past the body, feet outside it, exposed pads inside the terminals, header pins narrower than both pitches), `package.form_terminals` (the terminal count is not the form's lead count, or for a no-lead form with an exposed pad that count plus one), `package.envelope_derived` (a typed form's stored envelope differs from its derivation), `package.model_form` (a generated model on a generic form), `package.model_materials` (a body role listed twice); a library model's checks are `model.*` ([3D model library](#3d-model-library-project-container-and-markings-d0d6-as-built)). `package.form_terminals` replaced `package.body`.
- **Library folders (S3).** A package record carries its form, envelope, model and placement unchanged: none of them names another lineage or an asset, and materials are built-in `MaterialId`s of the project's `material_table`, not library references. `bundle::rewrite_refs` destructures them without wildcards so that a reference added later (an imported model's asset, M4) must be rewritten there; `a_generated_package_model_round_trips_through_a_folder` (automation) promotes a generated model with a role-material override and a placement to a folder and imports an equal copy.
- **Update diffs.** `updates::package_details` lists, for an instance's package revision change, the form family or each changed, added or removed `pkg_*` value and chip kind, the envelope (“model dimensions”), the model source or builder revision and each body role whose effective material changes, and the placement.

Both the prefix and the package fields are required in the file; the format is pre-release, so there is no migration. The samples take them from `samples::Kind` (`RESISTOR`: R, chip resistor form with a generated model; `CAPACITOR`: C, chip capacitor form with a generated model; `CONNECTOR`: J, generic moulded envelope); the demo and the Resistor template are resistors, the Connector template a connector, and the synthetic catalog gives resistors, capacitors and headers separate packages (`PackageDefinition::resize_envelope` keeps a chip form in step with its smaller size).

## Drawable symbol graphics (G1a, G1b)

A symbol unit is an ordered list of drawn graphics plus pins (`library/graphics.rs`; shapes and their maths in `geometry`). The design is in the reviewed graphics design; this section is the delivered contract of slices G1a (core) and G1b (views). Footprint graphics, layers, polarity and courtyards moved into F1 ([footprint data and rules](#footprint-data-and-rules-f1-core)).

- **Data.** `Unit { id, label, graphics: Vec<Graphic>, pins: Vec<Pin> }` and `SymbolDefinition.pin_text_height` (1.0 mm by default, below the 1.25 mm default of designator, name and value text). `Graphic { id: GraphicId, item }` with `Item::Shape { shape, width, fill }` or `Item::Text(Text { content, at, height, rotation, justify, visible })`. `Shape` is a line, open polyline, axis-aligned rectangle, circle, arc (counter-clockwise start and sweep in degrees) or closed polygon, in f64 millimetres with y up. `Fill` is `none`, `body` (theme symbol background) or `solid`. `TextContent` is a structured reference (`literal`, `designator`, `component_name`, `unit_label`, `field(lineage)`), never a placeholder string. The "value" is a `field` text of the lineage the author chooses.
- **Pins.** `Pin { terminal, position, direction, length, decorations, name, number }`. A pin is identified by its terminal; there is no pin ID and no stored electrical type or number. `position` is the connection end wires attach to; `direction` (right, up, left, down) points from it into the body. `Pin::decoration_shapes` defines the inversion bubble (0.4 × the 2.5 mm module, replacing the body end of the stub) and the clock wedge (inside the body edge) for every view.
- **Identity.** Unit and graphic IDs share the symbol's local namespace, so the local-ID rules protect graphic IDs: unique, below `next_local` and never a retired ID.
- **Removed (pre-release, no legacy reader).** `Unit.body_size`, `Anchor`, `SymbolDefinition::anchor()` (now `pin()`), `symbol.body` (now `symbol.unit_empty`), `symbol.anchor_duplicate` (now `symbol.pin_duplicate`) and `component.anchor_missing`/`anchor_unknown` (now `component.pin_missing`/`pin_unknown`).
- **Bounds (targets, enforced by `check_bounds`).** Limit errors: 256 graphics per unit, 1024 per definition, 1024 points per polyline or polygon, 8192 stored vertices per definition, literal text ≤ 256 bytes. Invalid-input errors: every point within ±10000 mm; stroke 0–5 mm; text height and `pin_text_height` 0.1–50 mm; radius not negative; finite angles with |sweep| ≤ 360°; pin length 0–50 mm; |pin text offset| ≤ 10 mm.
- **Blocking publish findings.** `graphic.degenerate` (no length or area, too few points, radius below 0.01 mm or zero sweep), `graphic.polygon_self_intersecting`, `graphic.invisible` (width 0 and no fill), `graphic.fill_open` (a fill on a line, polyline or arc), `text.empty` (blank or control characters), `text.too_long` (over 256 bytes or 16 lines), `symbol.pin_duplicate`, `symbol.unit_empty`, `component.text_field_unknown`.
- **Advisory lint.** `library::lint(&Draft, &Library, &Grid)`, appended to `component.check`/`component.check_drafts` for drafts only (stored revisions and decode never see it): `symbol.pin_off_grid` (1e-6 mm tolerance), `symbol.field_missing` (a unit without `designator` text) and `symbol.grid_sheet` (the symbol grid does not divide the 5 mm sheet grid, e.g. 2.54 mm).
- **Authoring grid.** `Drafts.grid: Grid { symbol_mm: 2.5, footprint_mm: 0.05 }` by default, each 0.01–10 mm. It is saved in `EditorFile.drafts`, undoable through `Document` and never revision data; `library.set_grid` replaces it. A per-source grid waits for folder libraries.
- **Core queries.** `Unit::bounds(TextMetric)` (graphics and pin stubs; text uses the stated approximation `chars × 0.6 × height` by `height`, four characters for unresolved content). Picking has one rule, `PlacedUnit::hit` on the resolved drawing (below); the definition-frame `Unit::hit` of G1a was removed once nothing called it. `schematic::occurrence_transform` (mirror across the local x-axis, quarter-turn rotation, then position; the one frame for drawing, pins, wire ends, picking and fit) and `schematic::placed_unit(project, occurrence)`, which resolves graphics, visible text (designator with unit label, component name, unit label, effective field text), pins, pin names and pin numbers through `instances::resolve`, `display_label` and `effective_fields`. Pin numbers are the designations the instance's binding maps to the terminal, joined by commas; without a physical choice they are `None`, never guessed. A pin name whose text equals its shown number is dropped (`PlacedPin.name` is `None`) and the number alone is drawn, so a pin never reads its number twice; the samples and templates (passives and connectors) hide pin names outright.
- **Updates.** `Change::ComponentRevision` plans report graphics added, removed and changed by ID per unit, pin direction/length/decoration/text changes and `pin_text_height` changes as presentation only, separately from pin moves.
- **Samples and templates.** `samples::two_terminal_header` (and the desktop templates and the synthetic catalog that use it) draws a 0.25 mm body rectangle with body fill, one pin per terminal pointing into it (`graphics::pin_toward`: direction from the side, length to the body edge, one module when 0), `designator` text above and `component_name` text below, all pins on the 2.5 mm grid. `samples::two_terminal` draws its kind's symbol (below).
- **Kind-specific symbols** (`library::symbol_style`, pure): `generate(SymbolKind, SymbolConventions, component, terminals)` draws original symbols after the general IEC 60617 / IEEE 315 conventions: resistor (IEC rectangle or US zigzag, by `SymbolConventions.resistor`, IEC by default), capacitor, polarised capacitor (straight + plate, curved − plate, + mark), inductor, ferrite bead, diode, Zener, Schottky, LED (two solid arrows), crystal, fuse, switch, push button, test point, NPN/PNP BJT, N/P MOSFET, ground and power; `IcBox` and `Connector` stay the samples' block and column layouts. Pin connection ends are on the 2.5 mm module; two-terminal kinds end at x = ±5 mm and hide pin names and numbers, transistors show their numbers. Terminal order: polarised capacitor 1 = +; diodes 1 = cathode (a molded package's band end); BJT 1 = B, 2 = E, 3 = C; MOSFET 1 = G, 2 = S, 3 = D (the common SOT-23 assignment, to verify against the datasheet). The drawing is a presentation default, never an electrical claim. `library.new_from_template` chooses with `samples::choose_symbol`: the request's `symbol`, else for a two-terminal skeleton the kind its designator prefix customarily names (`SymbolKind::for_prefix`: R, C, L, FB, D, LED, Z, Y, F, SW), else the row's suggested `symbol` (starter rows: tantalum and radial → polarised capacitor, ferrite chips → ferrite bead, SOD/SMA/MELF/axial DO → diode, axial resistors → resistor), else the form's (a chip's construction; a polarised other form → diode, else resistor). The row's suggestion also sets the default prefix (`catalog::default_prefix_for`: C for tantalum, FB for ferrite). A symbol whose terminal count differs from the package's is refused. The showcase draws C1–C2 as capacitors, C3 as a polarised capacitor and R1–R3 as resistors. `library.set_symbol_conventions { conventions }` (undoable, `Outcome::None`) sets `Drafts.symbols`, saved with the drafts and used by later template builds; existing symbols never change. The Symbol tab's grid popover offers it as *Resistor symbol*, and the template gallery shows the symbol its choices build.
- **Encoded size (measured, pretty JSON).** A symbol at every graphics limit (1024 graphics, 8192 vertices each with a corner radius, a rounded rectangle, 256 pins, long coordinates) encodes to 1 670 744 bytes, so ten such revisions fit the 16 MiB file; with on-grid coordinates it is still 1 370 150 bytes (twelve revisions), because indentation and keys dominate. 100 sample symbols encode to 267 802 bytes. The test requires at least eight full-limit revisions.
- **Open risk: file headroom for large symbols.** The reduced limits give less headroom than the design assumed: a project that keeps a dozen revisions of a symbol near the limits cannot be saved, even though typical revisions cost about 2.7 kB. Decide before the first release between a compact encoding (unindented JSON or a coordinate array form), pruning revisions no project references, or lower vertex limits. Until then, the limits stay as written and the measurement test guards the current numbers.
- **Deviations from the design.** Decoration sizes use the fixed 2.5 mm module instead of the authoring grid, because a placed instance has no grid. `Unit::bounds` takes no symbol argument and leaves out pin names and numbers, which resolve only on instances. `PlacedUnit.shapes` are `PlacedShape` records rather than tuples, and `PlacedPin` adds `line_end`. A zero arc sweep is the `graphic.degenerate` finding rather than a bound, so a draft can hold it.
- **Views (G1b).** The schematic canvas and the Component editor's Symbol view draw only `PlacedUnit` records from core and pick only through `PlacedUnit::hit`:
  - `schematic::placed_unit` is resolved once per document revision per occurrence; a dragged occurrence is drawn at its preview by offsetting the view, not re-resolved. `schematic::definition_unit(&Library, DefinitionUnit { symbol, unit, component, component_name, physical })` draws a unit being authored in its own frame: the designator reads `designator_prefix + "?"` (plus the unit label when the symbol has several units), pin numbers come from the working binding and package and are hidden without one, and a `field` text shows the component or field default (`instances::default_fields`), or the field name when there is none.
  - `PlacedUnit.fields` carries the values of fields the component marks `show_on_symbol` that no `field` text of the unit draws, centred and stacked 0.5 mm below the unit's drawn bounds at 1.25 mm, so the existing "show on symbol" choice keeps showing values on symbols that place no field text (such as the samples). They are upright; a click on one hits `SymbolHit::Field`, which stands for the unit as a whole. `PlacedUnit.occurrence` is `None` for a definition. `PlacedUnit::bounds(TextMetric)` and `PlacedText::bounds` give the drawn extent with resolved text lengths; the schematic fits the view and places new parts against them. `PlacedText.graphic` names the text graphic drawn (`None` for pin text and stacked values). The Place tool's ghost outlines the shapes and pin stubs of `definition_unit` for the component's first unit (numbers hidden), resolved once per component and revision.
  - Picking calls `PlacedUnit::hit(p, tol, TextMetric)` on the cached resolved drawing in sheet coordinates (a dragged occurrence offsets the pointer by its preview delta) with a 6 px tolerance, so fit, free-spot search and picking share one extent and the resolved text lengths: pins (stub, decorations, name and number) first, then text graphics and stacked values, then shapes, topmost first. A pin or anything drawn (body fill, outline, text, stacked value) selects the instance. The Component editor picks the definition frame through the same rule on `schematic::definition_unit`. Wiring still snaps to the nearest pin connection end within 9 px. In the Symbol view a pin hit selects the terminal and a drag moves its connection end on the symbol grid.
  - Strokes are mm × zoom with a 1 px minimum; `Fill::Body` uses the theme panel colour and `Fill::Solid` the stroke colour; concave polygons are ear-clipped in the app because egui fills only convex paths. Text is drawn with the bundled UI font at cap height = `height`, so its glyph box only approximates the core metric box. `graphics::upright(rotation, justify)` is the upright rule: a rotation in (90°, 270°] turns 180° and swaps left/right and top/bottom, covering the same box. Text under a mirrored occurrence stays readable: `placed_unit` reflects its box through the vertical justification (top ↔ bottom) instead of the glyphs, so after the upright rule it covers the image of its local box at every rotation, mirrored or not (`PlacedText.mirrored` stays false in the schematic). Text under 3 px is skipped.
  - Placing and dragging snap an occurrence's origin to the symbol grid (`Drafts.grid.symbol_mm`, 2.5 mm by default) instead of 0.5 mm, so on-grid pins stay on the grid. The palette's free-spot search steps by the whole number of symbol-grid pitches nearest the 5 mm sheet grid. The Component editor's Body rows were replaced by the drawing tools and selection properties in G2.

## Symbol drawing (G2)

The Component workspace's Symbol tab draws and edits symbol units with real tools. This section is the delivered contract of slice G2; footprint drawing is G3.

- **Rounded corners (core).** `Shape::Rect` has `radius` (every corner) and `Shape::Polyline`/`Polygon` have `radii`: empty, or one fillet radius per point (0 keeps a corner sharp). Both are omitted from files when unused. `geometry::rounded_path` turns a rounded shape into its straight edges and tangent fillet arcs (`Shape::primitives`); `bounds`, `distance` (and so picking), `flatten` (and so drawing and containment) use them, so bounds are tight and a cut corner is outside a filled shape. A fillet at a turn φ reaches `r · tan(φ/2)` along each edge (exact for right angles, so grid corners keep grid tangent points). `geometry::corner_radii_fit` is the validity rule — no rounded open end, no fold-back (turn over 179°), and the two fillets on an edge no longer than the edge — and `fit_corner_radii` shrinks radii to it. Overlapping fillets that a draft still holds are drawn shrunk in proportion, never folded. `transformed` keeps radii; a rounded rectangle under a non-quarter turn becomes a polygon with four equal radii. Bounds: radii are finite, not negative and absent or one per point (`check_bounds`). Blocking finding: `graphic.radius_too_large`. Updates diff a radius change as a changed graphic (presentation only).
- **Multi-line text (core).** Literal text may contain `\n` (at most 16 lines and 256 bytes; no other control characters: `graphics::printable_text`). `Text.line_spacing` (cap heights between lines, 1–4, default 1.6) is stored and carried to `PlacedText.line_spacing`. The core metric (`TextMetric::bounds(at, height, rotation, justify, TextSize)`) is as wide as the longest line and `height · (1 + (lines − 1) · spacing)` tall; justification places the whole block. `graphics::text_lines` lays the block out line by line (every line keeps the block's horizontal justification and centres on its own cap box; one line goes exactly where single-line text went) and `PlacedText::lines` applies the upright rule first, so views draw each line where the metric puts it. A multi-line text picks as one block.
- **Command.** `library.edit_graphics { draft, edits }` applies 1–256 `GraphicEdit`s in order to a copy of one symbol draft — `add { target: { unit }, item }` (new IDs from `next_local`, listed in order by `Outcome::GraphicsEdited { added }`), `replace { id, item }`, `translate { ids, delta }`, `remove { id }`, `set_pin { unit, pin }` (the terminal must exist on the owning component's draft or latest revision; nothing is inferred; a pin moves between units), `remove_pin { terminal }`, `set_pin_text_height { height }` — then replaces the draft through the bounds-checked draft edit. Any failure leaves the document and revision unchanged; it is one undo step. Footprint drafts are refused until G3 (`GraphicTarget` gains a footprint target then). JSON lines, MCP (`project_apply`) and the CLI expose it through the existing operation schema; gestures still commit whole bodies with `library.edit`.
- **Ribbon (Symbol tab).** Captioned groups of icon buttons: *Select*; *Draw* — split buttons Line ▾ (Line, Polyline), Rectangle ▾ (Rectangle, Rounded), Circle ▾ (Circle, Arc), then Polygon and Text ▾ (Text, Field). As in Solidcraft's sketch ribbon, a split button's icon runs the variant it shows (the last one armed) and its label with ▾ lists the variants; the » menu lists each variant. At the default tiled width (860 pt) Select, Draw, Pins and Arrange stay on the ribbon; Grid and Component go to »; *Pins* — Pin; *Arrange* — Rotate, Mirror, Duplicate, Delete (enabled with a selection); *Grid* — Grid (show) and Snap (toggle); *Component* — Passive and Connector templates and Publish. Icons are Solidcraft masters (`select`, `line`, `trace`, `rect`, `rect_rounded`, `circle`, `arc_center`, `polygon`, `text`, `point`, `params`, `spin`, `mirror`, `copy`, `delete`, `grid`, `snap`). Groups that do not fit go to a » overflow menu at the ribbon's end (as Solidcraft's toolbar does), so every tool stays reachable by a click.
- **Tools** (`part_editor/drawing.rs`, adapted from Solidcraft's sketch tool state machine): a tool collects snapped points and commits on the n-th; it stays armed after a shape. Line chains (each segment is its own graphic and commit). Polyline and Polygon collect points until Enter, a double-click on the last point, the Finish button in Properties, or (polygon) a click on the first point; a polyline mid-chain is never in the working copy. Rectangle and Rounded take two corners (Rounded uses the tool's corner radius, 0.5 mm by default, capped to fit); Circle takes centre and radius; Arc takes centre, start and end and runs the way the pointer went round the centre (Solidcraft's `follow_arc_turn`). Polyline and polygon tools round their interior corners with the tool's corner radius (fitted). Text places literal text and focuses its content field; Field places a designator, component name, unit label or a selected field's value (chosen in Properties; by default the first the unit does not show). Pin places the next terminal without a pin, or creates a terminal (with package terminal, pad and mapping) when all have pins; its direction points into the drawn body (`graphics::pin_toward`). Esc or a right click ends a chain, then the tool, then clears the selection; Cmd/Ctrl+Z pops a pending point before the global undo; Shift+R re-arms the last tool. Each finished action changes the working copy once and commits as one `library.edit` when the pointer is up (one undo step).
- **Keys** (checked against Solidcraft 4f3ac07's keymap — sketch L, R, C, D, P, X, O, T, G, Shift+R, Delete, Esc; model A, B, E, F, H, I, J, M, Q; held Space pans — and the schematic's P): L Line, Shift+L Polyline, R Rectangle, C Circle, A Arc (Solidcraft binds A only outside sketches), Shift+P Polygon (P is Project/Place), Shift+T Text (T is Trim), N Pin, Shift+F Field (F is Fillet), Cmd/Ctrl+R Rotate (Space is momentary pan), Shift+X Mirror (X is Construction), Cmd/Ctrl+D Duplicate, Delete/Backspace Delete, Shift+R repeat, Enter finish, Esc cancel. Rounded rectangle has no key. Plain keys act only while no text field has the keyboard. The Schematic sheet reuses Cmd/Ctrl+R (turn the selected occurrence 90° counter-clockwise) and Shift+X (mirror it left to right) with the Select tool; with nothing selected the keys are not consumed.
- **Snapping** (`part_editor/snap.rs`, adapted from Solidcraft's `drag_snap.rs`, no constraints): within 7 px, in order: an endpoint or vertex (and text anchors and pending points), a pin connection end, a segment midpoint, a centre, the origin, onto a curve, horizontal/vertical alignment with a point (dashed guides; the other axis on the grid), else the symbol grid. Ctrl/Cmd or Alt suppresses snapping; the Snap button turns it off. The snapped point shows a marker with a label (End, Pin, Mid, Centre, Origin, On).
- **Selection** (`part_editor/arrange.rs`): click selects a pin or graphic through `PlacedUnit::hit`; Shift toggles; dragging from empty space draws a box — rightward is a window (wholly inside), leftward a crossing (touching). The box measures the same resolved drawing the click picks (resolved placeholder text; hidden text is not drawn, so no box selects it and it offers no snap). Views measure text with `symbol_view::metric`: the core metric with the bundled font's mean capital advance, so the box that picks and outlines text contains what is drawn. ## Footprint data and rules (F1 core)

The footprint types are in `library/footprint.rs` (solved data), `library/graphics.rs` (drawings) and `library/footprint_source.rs` (the parametric source and the evaluator seam); this section is the delivered core rule set, and [F1/F2 as built](#footprint-geometry-editing-and-3d-f1f2-as-built) covers the geometry, editors, 3D and evaluator. Every rule is a `library::publish_findings` finding, so `library.publish`, document decode and `component.check` apply the same list; advisory rules are `library::lint` (drafts only, `blocks: None`).

- **Blocking publish findings** (codes, objects name the pad or graphic local ID):
  - `footprint.pad_count` (1–1024 pads), `footprint.pad_size` (a primitive's size 0.01–10000 mm), `footprint.pad_shape` (rounded-rect ratio 0–0.5 and a non-negative cap; a custom outline that is closed, has area and does not cross itself), `footprint.pad_number` (≤ 256 bytes);
  - `footprint.terminal_required` (SMD or plated-through without a terminal; a terminal-less copper land must be `Mechanical` explicitly), `footprint.terminal_forbidden` (non-plated hole or fiducial with one), `footprint.pad_terminal_unknown`, `footprint.terminal_without_pad`;
  - `footprint.pad_side` (through-hole kinds record the top side), `footprint.hole_kind` (plated-through needs a plated hole, a non-plated hole an unplated one, SMD and fiducials none), `footprint.hole_shape` (positive drill; a slot at least as long as wide);
  - `footprint.hole_outside_land` (the drill, or a pad via's drill, is not inside the land), `footprint.paste_window_shape` (a window needs a closed shape with area), `footprint.paste_window_outside_pad`, `footprint.aperture_duplicate` (window and via IDs are unique per pad). Containment flattens both outlines at `CHECK_CHORD_MM` = 1 µm and allows twice that; a non-convex land also refuses crossing edges;
  - drawings: the symbol graphic rules (`graphic.degenerate`, `graphic.radius_too_large`, `graphic.polygon_self_intersecting`, `graphic.invisible`, `graphic.fill_open`, `text.empty`, `text.too_long`) plus `graphic.fill_body` (no body fill on a footprint), `text.content_kind` (component name or unit label on a footprint), `footprint.courtyard_open` (courtyard items are closed shapes);
  - polarity: `footprint.polarity_pad_unknown`, `footprint.polarity_marker_unknown` (a marker is a silkscreen or assembly graphic of this footprint, listed once, at most 8);
  - source (no evaluator needed): `footprint.param_name` (identifier syntax), `footprint.param_reserved` (the `pkg_` prefix belongs to package values), `footprint.param_duplicate`, `footprint.param_expr` (every stored expression is non-blank printable text ≤ 256 bytes; the grammar is the evaluator's), `footprint.solve_failed` and `footprint.over_constrained` (the stored solve status), `footprint.source_pad_unknown` (roles and array keys name stored pads, each pad owned once; keys name an array; seeds have a role), `footprint.override_orphaned`. Advisory lint adds `footprint.pad_outside_courtyard` (a pad not inside any closed courtyard shape) and `footprint.silk_over_pad` (a silkscreen stroke over same-side copper). `footprint.stale`, `footprint.evaluator_rev`, `footprint.anchor_missing`, `footprint.owned_curve` and `footprint.pad_shape_unclassified` need the evaluator and belong to F2.
- **Bounds** (`check_bounds`, so drafts too): the contract constants, plus footprint graphics within the symbol limits (1024 graphics, 1024 points per shape, 8192 stored vertices per definition), at most 8 polarity markers, pad numbers ≤ 256 bytes, finite pad defaults within ±10000 mm, and on the source every id, list, comment and nested expression (`FootprintSource::expressions`). `layout::validate` refuses a board whose placed footprints store more than `MAX_PLACED_GRAPHIC_VERTICES` = 262 144 graphic vertices (a target).
- **Advisory lint** (`FootprintDefinition::lint`): `footprint.courtyard_missing`, `footprint.polarity_missing` (more than two pads and no polarity pad), `footprint.mask_web` (two openings on a shared copper side closer than `MIN_MASK_WEB_MM` = 0.1 mm, an estimated default, with a 1 nm rounding allowance so a web of exactly the minimum passes; at most 64 reported). Nothing is inserted automatically.
- **Graphic edits.** `library.edit_graphics` also edits footprint drafts: `add { target: { footprint: { layer, side } }, item }`, `replace`, `translate`, `remove` (a removed marker leaves the polarity), `set_layer { id, layer, side }` and `set_polarity { polarity }` (the pad and markers must exist; markers on silkscreen or assembly). Unit targets, pins and pin text refuse on a footprint; layers and polarity refuse on a symbol; a graphic a source role derives refuses with `conflict` (edit the role). Any failure leaves the draft unchanged.
- **Templates.** `library::templates::footprint` is pure: `courtyard_from(pads, outline, excess, round_to)` (the pad and envelope box grown and rounded outward), `silk_outline` (the envelope 0.15 mm outside, broken around each pad's mask opening plus 0.1 mm clearance and half the stroke) and `add_standard_graphics` (assembly outline 0.10 mm and designator, silkscreen 0.15 mm and designator, courtyard 0.05 mm at 0.25 mm excess and 0.05 mm rounding; polarity is never added). The values are estimated defaults, not copied tables. The samples and the synthetic catalog use them; the parametric family templates (`FootprintEdit`s) are F5.
- **Update preview.** Footprint pads are compared by `PadId`: a retired pad (its copper-touching tracks warned explicitly), an added pad (marked unresolved when it needs a terminal and has none), and per kept pad each changed aspect — moves, reshape, turn (canonical per shape symmetry, so a rectangle at 180° is unchanged), kind or side, landed terminal, number (display only), hole, mask and paste, vias. Footprint graphics are counted per layer as presentation only; polarity, pad defaults and array growth or shrink (new and retired pad IDs per array, from the source keys) are listed.

## Footprint geometry, editing and 3D (F1/F2 as built)

F1 and F2 were built as five parallel tasks on one contract commit and merged on 31 October 2026. The contract note was folded in here and removed. Pre-release: the old rectangle-only `Pad { id, terminal, position, size }` and `datum_offset` were replaced, with no legacy reader.

- **One pad geometry.** `library/footprint/geometry.rs` is the only place a pad, hole or opening becomes an outline. `PadShape::corner_radius` (ratio of the short side, clamped to half of it, then the cap) and `PadShape::grown(by, tol)` give each shape as an exact core `Shape` in the pad frame (rounded corners keep their radii; only custom bulge arcs are flattened, within `tol`). Growing is a mitred offset: sharp corners stay sharp and rounded ones grow with the sides, the same rule the native mask openings use. `PadShape::{outline, flatten}`, `Outline::flatten` (through `bulge_arc`), `HoleShape::shape`, `Hole::shape`, `offset_polygon` and, on `Pad`, `frame`, `land`, `hole_shape`, `mask_expansion`, `mask_opening` and `paste_openings` build on them. Inherited paste is none for hole kinds and fiducials. `PadKind::terminal_rule` (`Required`, `Forbidden`, `Optional`) is the rule `footprint.terminal_required`/`terminal_forbidden` enforce and the inspector offers. Checks flatten at `CHECK_CHORD_MM` (1 µm); display, picking and display-only 3D layers at `PAD_ARC_TOLERANCE_MM` (2 µm). Native 3D copper is the one exception: `crates/solidcraft-integration/src/pad_outline.rs` re-derives the same corner, grow, slot and custom-offset rules as exact Solidcraft contours (lines and arcs, not flattened), and `native_contours_match_the_core_pad_geometry` holds the two equal for every primitive shape and grow value.
- **Placed queries** (`layout/placed.rs`): `placement_transform`, `placed_pads` (every pad, including terminal-less and unconnected ones) and `placed_graphics`; on `PlacedPad`, `center`, `pad_transform`, `on_copper` (plated-through on every layer, a bare hole on none), `outline`, `holes` (its hole, then pad vias) and `contains`; `pick_pad` and `pick_graphic` (topmost first, visibility filtered). `placed_graphics` resolves `Designator` and `Literal` text; other content is empty for now.
- **PCB 2D** (`apps/pcbcraft/src/pcb_editor.rs`) draws pads, holes, pad vias and the silkscreen, courtyard and assembly layers through those queries, with per-layer toggles and a bottom view (mirrored in x; the far side dimmed). Hidden layers do not pick. Routing snaps to visible pads that have a net and copper on the routing layer. The board drawing is built once per revision; selection, layers and camera do not rebuild it.
- **Footprint tab** (`apps/pcbcraft/src/part_editor/footprint_*.rs`) edits every typed pad property through the kit: kind, number, an explicit terminal (required, optional or forbidden by kind, never inferred from the number), side, position, rotation (canonical per shape symmetry), shape (custom outlines are read-only: a sketch makes them), hole, mask and paste, plus the datum rotation and the footprint-wide defaults. The canvas draws lands, holes, vias, display-only mask and paste openings, the graphic layers and the envelope from the core geometry, and picks by the land outline. Pads derived from a source are read-only here.
- **Native copper** (`crates/solidcraft-integration/src/project.rs`, `pad_outline.rs`): each pad is real copper in its placed frame (pad and datum rotation through `placement_transform`; a bottom placement mirrors it). A rectangle with no hole whose sides line up with the component's axes stays a parametric box (`pad_*_length`/`_width`); every other shape is a sketch of lines and exact arcs (`pad_outline::Contour`, the same corner and offset rules as the core) extruded by the copper thickness. Plated-through pads get a land on each face and a plated barrel (`PLATING_MM`, an estimated 25 µm) through the laminate; pad vias get barrels; the laminate's drills are one cut; bare holes have no copper. The display-only soldermask (`appearance.rs`, `appearance/region.rs`) has openings that follow each pad's mask rule (tented lands stay covered) and holes, and the finish follows the land with its bore. Display layers are never saved in `.solidcraft`.
- **Evaluator** (`crates/solidcraft-integration/src/footprint/`): `SketchEvaluator` implements `FootprintEvaluator` on Solidcraft's public sketch solver and expression language: the canonical-sketch check from the [F0 spike](footprint-spike.md), parameters with typed `pkg_*` package values, sketch edits and constrained pad templates whose size dimensions bind through `Constraint.param`, a solve that refuses folds and flips, the copper-only profile pass, classification into typed shapes or exact custom outlines, holes, mask/paste, vias, arrays (linear, dual row, per-side quad, staggerable grid; skips and numbering), overrides, curve-derived graphics, the datum (`FootprintSource.datum: Option<DatumRole>`), a 1e-6 mm quantizer and the result hash. `cargo xtask wasm-footprint` runs its golden-hash tests under Node (it is not part of `xtask ci`); the spike module was removed and stays in git history for F6's scratch-`Session` bridge. The copper pass keeps every non-construction curve that no other role (hole, paste window, graphic) owns, so a stray unassigned curve counts as copper and makes the pad it crosses `footprint.pad_shape_unclassified` (a refusal, never a silent change). Array instances take the seed's pad at the full instance turn, overrides apply at that turn, and only then is the rotation folded per shape symmetry by `Pad::fold_rotation`, which turns the hole offset, slot, vias and paste windows by the removed amount so nothing moves. `commit` keeps only the keys generated now: a retired instance's key is dropped with its pad and its ID never returns (`next_local` only grows).
- **Commands.** `library.edit_footprint` (atomic: one evaluation; a blocking finding refuses and changes nothing), `library.assign_terminals` (an explicit rule, `ByPackageDesignation` or `Explicit`, previewed with `confirm: false`; nothing is inferred without the command), the `library.footprint_preview` query, `footprint.derived` (Rhai pad generation refuses on a sourced footprint) and the publish freshness check `footprint.stale`. `library.publish` runs the pure publish findings first, so they are reported even without an evaluator; a sourced footprint then needs the evaluator to prove its stored pads re-evaluate unchanged: `check_fresh` compares the re-evaluated result hash and the stored pads (without their authored terminals), graphics and datum, so a body edited with `library.edit` while keeping the source is `footprint.stale`. The desktop, CLI and MCP all pass `SketchEvaluator` through `Engine::apply_with` (and `query_using`); `Engine::apply` passes none, and source edits then refuse with `footprint.evaluator_required`.
- **Board copper (since F4/F5).** Board checks and track connectivity use each pad's exact outline; see [F4/F5 as built](#footprint-sketch-ui-and-templates-f4f5-as-built). They follow the pad's copper layers: an opposite-side SMD pad is on the other layer, and a plated through-hole pad (`WorldPad::through`) is on every layer, so a track on either side connects to it. Labels name pads by number (`layout::pad_labels`), never by `PadId`. Trim, fillet, offset, split and mirror sketch edits are F6 (the scratch-`Session` bridge).

## Footprint sketch UI and templates (F4/F5 as built)

F4 (the sketch UI on the Component Footprint tab) and F5 (family templates, explicit derived courtyard and assembly roles, footprint lint and board courtyard checks) were built as four parallel tasks on one contract commit and merged on 31 October 2026. The contract note was folded in here and removed. Every gesture, form and panel edit is one `library.edit_footprint` (or one `library.footprint_from_template`); a refusal leaves the draft unchanged. Courtyard and assembly outlines are never inferred: they are authored graphics or explicitly added `Derived` graphic roles.

- **When the tab sketches.** A footprint with a parametric source, or one without explicit pads, shows the sketch ribbon (`PartEditor::footprint_sketching`), in this order so the pad and constraint tools stay on the ribbon at narrow widths and the rest folds into » first: Pads (From template; pad split button Rect/Rounded/Round/Oblong; Custom; array split button Row/Dual row/Quad/Grid; Drill/Slot), Constrain (Dimension, a split button of the geometric constraints showing the last used, and All dims; enabled once a source exists), Component (Publish), Sketch (Select, Line, Arc, Circle, Rectangle), Layer (Construction, Silkscreen, Assembly, Courtyard), Terminals, Artwork and Show. A footprint with explicit pads keeps the F1 pad tools. Pads placed by the sketch tools get the next free number and land no package terminal: binding is the explicit `library.assign_terminals`, as for templates.
- **Sketch tools** (`apps/pcbcraft/src/part_editor/footprint_tools.rs`, canvas in `footprint_tools_canvas.rs`). A small state machine after the Symbol drawing tools: clicks collect snapped points (`snap.rs`) until the gesture is complete; Esc or a right click ends the gesture, then the tool; the tool stays armed; Shift+R re-arms the last tool. Pad tools place one constrained template pad per click, sized by the named parameters `pad_l`, `pad_w`, `pad_d` (Space turns the next pad a quarter). Custom converts a template pad to its outline or starts a profile pad. Arrays are a seed pad plus `AddArray` (linear and dual row from pad 1 and a direction line; quad from the centre with per-side counts; grid from A1 with skips). Drill puts a concentric plated hole on a pad or makes a bare NPTH pad; Slot takes both ends. Line, Arc, Circle and Rectangle draw on the active layer: construction geometry, or curves with a `GraphicRole` (`GraphicSource::Curves`) on silkscreen, assembly or courtyard. Select picks pads, sketch points and curves, moves them (`SketchEdit::Move`/`Drag`) and deletes them. A gesture that needs ids it creates in the same commit (an array's seed and direction line, a curve's graphic role, a drill circle) learns them first from the core's pure `footprint_edit::preview` and the evaluator's `apply_sketch`; both are deterministic, so the engine allocates the same ids. Keys (checked against Solidcraft's keymap and the Symbol tab): L, A, C, R draw; D Dimension; N pad; Shift+N dual row; H drill; Shift+H slot; X toggles Construction; Delete removes; held Space pans.
- **Dimensions, constraints and drags** (`footprint_dims.rs`, canvas in `footprint_dims_ui.rs`). The overlay draws the sketch in Solidcraft's solver colours (free, defined, conflict) from `solve_report` (status, degrees of freedom, free points and curves, conflicting and redundant constraints), dimensions laid out by Solidcraft's `dim_layout_reaching` (driven values in parentheses, R/Ø prefixes, a bound parameter before its value, `len = 2.5`) and constraint glyphs. The Dimension tool takes points, a line, two lines or a curve; where it is placed chooses aligned, horizontal or vertical as in Solidcraft; its field takes a value, a parameter name or `name = expression`, which defines the parameter and binds the dimension (`DimValue::Param`) in one commit. Double-clicking a label edits it in place; a refused value, or an unknown bare name (`Unknown parameter pad_q — use pad_q = <value> to define it`), keeps the field open with the reason. By default (`DimDetail::Key`) the canvas labels the dimensions of independent parameters, each parameter once, and unbound driving dimensions; dimensions bound to a derived parameter (a template's `seed_*`, `pad_x`, `paste_*`), to an expression (a rounded pad's corner) or driven are left out, as are the glyphs of pad-owned template, drill and paste curves, unless the selected dimension, the hovered parameter or the selected pads, points or curves touch them. All dims (Constrain group) shows everything. A label that would overlap one already placed steps aside along a short leader, else it is left out that frame; an expression-bound label shows only its value. Constrain tools commit once their picks are complete. Dragging a free point previews each frame with `LiveSketch::drag` (a held solve under Solidcraft's `Budget::frame`, then `move_point_towards`, else stays put) without touching the document; the release commits one `SketchEdit::Drag`. The overlay takes the pointer first (labels, glyphs, Dimension and Constrain picks, free-point drags), and the sketch tools skip a frame it took; selecting a pad or sketch entity drops a selected dimension and vice versa.
- **Parameters panel** (`footprint_params.rs`, `footprint_params_ui.rs`) in Properties: package values (`pkg_*`) read-only, then each parameter's name and expression as editable cells, its typed value and every reader (`view::readers`: dimensions, other parameters, arrays, the derived courtyard, pad rules, overrides, graphic widths and expression-placed points, as in "used by 1 dimension, array, courtyard"); hovering a row highlights its dimensions. Each change is tried on the working copy first and then sent (`SetParameter`, `RenameParameter`, `RemoveParameter`); removing a parameter anything reads is refused with a sentence naming the readers.
- **One commit path.** Tools, dimensions, constraints, drags and the panel queue their edits in one outbox; `PartEditor::commit` sends it once per frame as `library.edit_footprint` (the working copy first when it has unsent edits). A gesture finished while the outbox is occupied is refused with a notice, never overwriting the waiting one; if the working copy sent ahead of a held gesture was refused, the held gesture is dropped with a notice instead of being sent against ids staged elsewhere.
- **Family templates** (`crates/editor-core/src/library/templates/footprint_family.rs`). `FootprintTemplate::{Chip, GullWing, Qfn, PinHeader}` with defaults derived from the package (`FootprintTemplate::defaults`; literals when the package has no values). `build` runs a short sequence of steps whose edits are pure functions of the template and of the ids earlier steps created, unevaluated on one clone (`footprint_edit::apply_unevaluated`), and evaluates once at the end. Positions are dimensions bound to named parameters measured from the sketch origin, so editing a parameter re-solves the footprint. 2-terminal chip: `pad_x = (gap + pad_l) / 2`, corner ratio 0 for a plain rectangle, optional pin-1 polarity. SOIC/SOP gull-wing: a seed plus a dual row along the body length, pin 1 bottom left, counter-clockwise. QFN/DFN: per-side quad, an exposed pad at the origin with dimensioned paste windows (`paste_w/h`, at most `MAX_PASTE_GRID` per side) and an optional via grid; the exposed-pad terminal is left for an explicit choice. Pin header/DIP: plated drill role, grid or dual row, a rounded pin 1 through `SetOverride`. Every template adds an explicit `Derived` courtyard role (`CourtyardFromExtents`, parameter `courtyard_excess`, default `TEMPLATE_COURTYARD_EXCESS` 0.25 mm) and an assembly role, and a silkscreen pin-1 dot clear of copper where polarised. All values are estimated defaults, not copied tables or a compliance claim. `library.footprint_from_template { draft, template, replace }` builds into an empty draft only (`footprint.template_not_empty`) unless `replace` is true; then `footprint_family::rebuild` drops the source, pads, polarity and role-solved graphics (`footprint_family::cleared`, authored graphics and pad defaults kept) and builds on the same clone, so clear and build are one undo step. It needs the evaluator; its CLI and MCP schemas are generated.
- **Template picker** (`footprint_template_picker.rs`). "From template" opens the docked "Footprint from template" dialog (a `kit::DialogPanel`; "Replace footprint", destructive, when the footprint is not empty, replacing it in the same atomic step): the family (suggested from the package), its prefilled form as text (short labels, full meaning in tooltips), a ghost of the pads Build would make on the canvas (the same pure `footprint_family::build` on an empty copy, rebuilt only when the form or package changes), a warning when the pads that land terminals differ in number from the package's terminals, Build (one `library.footprint_from_template`; the view refits when the pads arrive), and afterwards the docked Assign pads by number dialog. Build leaves pads without a package terminal, and the dialog says so ("Builds 2 pads; assign them to terminals afterwards"). Assign by number shows a preview of each pad and the terminal it would take (`footprint_edit::assign_terminals`, the `confirm: false` result) before `library.assign_terminals { confirm: true }`. Counts the package cannot divide fall back to the family's usual four per side or row. A template moves the draft's silkscreen designator off its pads.
- **Footprint lint** (advisory, `library/footprint/checks.rs`) adds `footprint.silk_width` (an unfilled silkscreen stroke below `MIN_SILK_WIDTH_MM` = 0.1 mm) and `footprint.text_height` (silkscreen text below `MIN_SILK_TEXT_HEIGHT_MM` = 0.6 mm); both are estimated defaults. Footprint findings name pads by number (the id only when the number is empty). Footprint findings show in Issues (their one home); locating one selects the pad, or outlines the graphic, it names on the Footprint tab.
- **Board courtyards** (`crates/editor-core/src/layout/courtyard.rs`). `placed_courtyards` places each part's courtyard-layer shapes; `board.courtyard_overlap` reports, once per pair, two placements on the same side whose courtyards share interior area (abutting edges pass). A part without a courtyard is not checked here; the footprint lint reports it. Beyond `MAX_CHECKED_COURTYARDS` shapes or `MAX_OVERLAP_FINDINGS` findings the check adds one `board.check_limit` finding instead of passing silently; it is an error (the unchecked geometry may hold uncounted errors) that names the board (`ObjectRef::Board`), so locating it frames the board. The PCB view tints both parts' courtyards of each overlap, and locating a two-part issue from Issues selects both parts and frames them.
- **Exact board copper** (`crates/editor-core/src/layout/copper.rs`). `CopperRing` is one copper outline on the board (pad outline from `WorldPad::outline`, or a track: the stadium a round aperture sweeps, `layout::track_shape`) with exact bounds and a slack; `BoardCopper` holds the connected pads' rings, is built once per document revision and moves for the placement drag preview (`moved`). Clearance, connectivity, airwires, routing clearance and the route snap use them, comparing only rings near each other through a uniform grid of their bounds (`layout/grid.rs`, `BoundsGrid`; see [PCB realism](pcb-realism.md#opening-the-3d-view)). Curved edges flatten within `CURVE_SLACK_MM` (= `PAD_ARC_TOLERANCE_MM`): straight-sided copper is exact, and so are track caps (measured from the track centre line less half its width); on other curves, touching is accepted within the slack and clearance is conservative (may flag up to the slack early, never misses). `WorldPad` records mirroring, so bottom-side asymmetric pads land as the placement transform puts them. ## SVG artwork import (F-SVG)

SVG logos and marks become ordinary, editable library graphics on a symbol unit or a footprint's silkscreen or assembly layer. Design: F-SVG and FD15 of the footprint and 3D design.

- **Path.** The app (Import SVG…) or the session (`library.import_svg`) reads the file with `pcbcraft_io::artwork::read_svg` (`.svg`, UTF-8, at most 1 MiB). `pcbcraft_solidcraft::svg::convert(text, Options { scale, tolerance_mm, fallback_stroke_mm })` returns an `Artwork { items, size, notes }` centred on its bounding box; `Artwork::edits(target, at)` makes the `GraphicEdit::Add` batch, refusing the courtyard. One `library.edit_graphics` applies it: atomic, one undo step, new IDs in the outcome. No core command was added.
- **Reader.** Geometry is Solidcraft's public `solidcraft_engine::io::read_svg`: every path command, line, rect, circle, ellipse, polyline and polygon, nested transforms, user units scaled to millimetres from the root `width`/`height` over the `viewBox` (96 user units per inch without units) and y flipped. That reader returns curves without their element, so the converter walks the XML (`quick-xml`) for per-element presentation — `fill`, `stroke`, `stroke-width`, inherited through groups and `style`; `display:none`, `visibility:hidden`, `defs` and other non-rendered content skipped — and passes the reader one element at a time inside its ancestors' transforms. It probes each frame's map with two unit lines, so stroke widths and rectangles use the same transform as the curves.
- **Mapping.** Circles stay circles, also when a path draws one as arcs. Circular arcs stay `Shape::Arc`. A rectangle stays `Shape::Rect` with its corner radius while its frame is axis-aligned (and uniform when rounded); otherwise it becomes path data. Straight runs become polylines or polygons, and a circular arc tangent to the straight edges on both sides becomes that corner's fillet radius (`corner_radii_fit`). Cubic and quadratic Béziers and ellipses are flattened within the chord tolerance (default 0.01 mm, 0.001–1 mm; the step count follows the second-derivative bound, at most 256 per curve; the test samples the true curve). Strokes keep their width (scaled by the frame and the user scale). A filled closed loop becomes a `Fill::Solid` polygon, circle or rectangle with its stroke as outline width (0 without one); an open filled subpath closes as SVG fills it.
- **Holes (FD15).** Graphics have no polygon with holes, so a filled element whose loops nest (a ring, a letter O) is imported as outlines at its stroke width or the target's default stroke, and the notes say so. Filled regions with holes follow when outline regions land.
- **Skipped and reported.** Text (convert it to paths), images, `use` references, elements without fill or stroke, and elements whose transform collapses them.
- **Bounds (refusals, nothing imported).** 1 MiB of text, 2048 drawn elements, 32 768 reader segments; then the graphics limits: at most 256 graphics per import (`MAX_GRAPHIC_EDITS`, also the per-unit limit), 8192 points, 1024 points in one filled region (outlines split), a stroke of at most 5 mm, every point within ±10000 mm, scale 0.001–1000. The draft edit then applies the definition's own bounds.
- **Desktop.** The Symbol tab's Draw group and the Footprint tab's Artwork group have Import SVG…; the file service's native picker chooses the file, reading and conversion run on worker threads, a dialog shows the size and takes the scale (and the silkscreen or assembly layer), and the artwork lands at the view centre (on the grid) as one undo step. On the Symbol tab the new graphics are selected for moving; the Footprint tab does not select graphics yet. On a footprint with a parametric source, authored shape graphics are kept as the core keeps them.
- **Tests.** `crates/solidcraft-integration/src/svg/tests.rs` (original fixture `svg/mark.svg`: rounded badge, filled dot, cubic wave, rotated triangle, ring with a hole, rounded tab; Bézier deviation at three tolerances; arcs, units and scale; refusals; placement; inheritance), `crates/io/src/artwork.rs`, and `crates/automation/src/session/svg_tests.rs` (JSON import into a symbol and footprint silkscreen, refusals leave the revision unchanged, one undo step, generated catalog and MCP tool).

## Generated 3D models and placement (M1–M3 as built)

M1–M3 of the footprint and 3D design (section B) were built as three parallel tasks on one contract commit and merged on 31 October 2026; the contract note was folded in here and removed. Every body of a generated model is a physical material, which Solidcraft's product look renders, and every instance of a package revision shares one native model definition. Package data, frames, lead order, `pkg_*` values and findings are in [designator prefix and package form](#designator-prefix-and-package-form); materials are in [materials](materials.md#package-materials).

- **Materials (M1).** `materials` (core row 5a): `MaterialId` (24 built-in physical materials), `MaterialCategory`, `MaterialDef` with `Coat`, `Transmission`, `SurfacePattern`, and `SourceNote` citations or the `EST` key; `builtin(id)` and `all()` read one cited table, each definition is checked against the opaque-surface bounds (`MaterialDef::validate`). A project stores only `MaterialId`s and records the table revision it was built against (`Project.material_table`, checked by `validate::project`): a `.pcbcraft` file of another table revision is refused (`unsupported`) rather than reopened with different looks. The saved `.solidcraft` model carries each body's opaque projection. Deviation from the spec (§4.3 asks the snapshot to copy every `MaterialDef` it uses): the definitions are not copied yet, because the table is app data with one revision before the first release; changing a built-in value means raising `BUILTIN_REVISION`. Copying definitions arrives with user materials, which become a revisioned library definition kind. User materials, when they exist, become a revisioned library definition kind.
- **Model sources.** `PackageModel` is `envelope { material }`, `generated { family_rev, materials }` (per-`BodyRole` overrides of `default_material`) or `library(LibraryModel)`, an exact revision of a library model with its lead map ([D1](#3d-model-library-project-container-and-markings-d0d6-as-built)). Pre-release: no legacy readers.
- **Builders (M2, `crates/solidcraft-integration/src/models/`).** `build_definition(&mut Native, component, &PackageDefinition)` writes one native component named `pkg<id>r<rev>` with named parameters `pkg<id>r<rev>_<name>` (`PARAMETER_PREFIX`), so the saved model stays parametric: chip (ceramic or ferrite body, two tin terminations, a black overcoat on a resistor), gull-wing (SOIC on two sides, QFP on four; body on its standoff, arc-bent lead profiles, body cut around the lead roots, pin-1 dimple), no-lead (QFN/DFN terminals flush with the underside and side faces, optional exposed pad) and pin header (PBT base, gold pins). `family_rev` is 1 for every family; a model authored against another builder revision, an envelope, an imported model or a generic form is refused (`model.unsupported`). Each body carries a `BodyRole`, a `MaterialId` and, when the package lists exactly one terminal per lead, its terminal (never guessed); they are stored in `org.pcbcraft.electronics.models.N` chunks (`MODEL_BODIES_KEY`, ≤ 48 KiB each, at most 200; overflow is a refusal), and the opaque PBR projection is saved through `appearance.assign`, so plain Solidcraft reopens the model with its looks. `models::look` maps a `MaterialDef` to the saved projection and to the product look (clear coat, pattern) the views draw per triangle; display-only parts are never saved.
- **Board and preview.** `project::build` builds one definition per package revision and places one occurrence per instance on the seating plane (top or bottom). The board places a footprint by its datum (`layout::placement_transform` undoes it), so the joint holds the model at its placement in the datum frame; `model_frame(datum, placement)` is the same pose in the footprint frame, which the 2D drawing and checks use. Envelope boxes are placed the same way (translation and rotation), so a quick action on an envelope package shows on the board and in the saved model; their display-only terminations, overcoat and fillets are drawn only while the placement does not turn the box. A generated chip whose placement does not turn it also gets the display-only solder fillets, against its real termination bodies. The Component 3D preview builds the same definition (or the envelope) and moves it by the placement. The builders check the core's `PackageForm::range_problems` first, which hold every rule the builders need (lead exit height and bend room of a gull-wing lead, a header's pin above the body), so a published form always builds (`models::tests::every_form_the_core_accepts_is_built`).
- **Placement (M3, `library/package_fit.rs`).** `fit_leads` is a 2D Kabsch fit (`FitRotation::Free` or `Quarter`) of lead contacts onto pad centres, then seats the lowest contact on z = 0; it reports per-terminal residuals, the rms and `mirrored_better` (a reversed pin order would fit better). `form_pairs` pairs `lead_points` with the copper pads of each terminal (explicit mapping only). Quick actions (`QuickAction`): rotate by quarter turns about the body centre, flip, stand up, seat, centre on pads and pin 1 to pad 1 (the last two need the landing footprint). Advisory findings in the footprint draft checks: `package.lead_off_land` (more than `LEAD_OFF_LAND_FRACTION` = 25 % of the land width across, or outside, an estimate), `package.lead_unseated` and `package.body_below_board`. Library models check their bounds against the envelope (advisory `model.bounds`, `BOUNDS_TOLERANCE_MM` 0.1 mm); still deferred: the model crossing the courtyard and a polarised package without an asymmetric feature (CE-02). `spacing_mismatch` names a residual no placement removes (lead spacing against pad spacing); host-supplied pairs are checked against the package's terminals and the landing footprint's pads (`check_pair_ids`).
- **Commands.** `library.edit_package { draft, edits: Vec<PackageEdit> }` (`SetForm`, `SetModel`, `SetPlacement`, `ApplyQuick`; 1–256 edits, atomic, one undo step; pad-relative quick actions use the one footprint draft landing the package) and `library.fit_leads { draft, pairs, rotation, confirm }` (`Outcome::LeadsFitted { fit, applied }`; empty `pairs` derives them from the typed form; `confirm: false` only reports). Several footprint drafts landing the package is `package.footprint_ambiguous`. CLI and MCP schemas are generated from these types.
- **Component 3D tab** (`apps/pcbcraft/src/part_editor/model_*.rs`, `viewport/display.rs`). The Body section (`model_body.rs`) chooses the form family (generic, chip, gull-wing, no-lead, pin header) and a preset (`samples::Preset`: 0603, 0805, SOIC-8, TQFP-32, QFN-16, DFN-8, headers 2×5 and 1×2), shows the family's typed parameters (one `SetForm` when a field is left), the model source (generated or envelope, `SetModel`) and "Lands from body", which replaces the footprint's terminal lands with lands centred on the leads (`samples::form_lands`, a working-set edit). A new component on a generated model starts from the New-from-template gallery ([libui](#component-workspace-catalog-and-package-templates-libui-as-built)); the presets remain test and sample data. Placement is one control: numeric translation and rotation fields (one `SetPlacement` when a field is left; plain numbers, not expressions, a deviation from the spec), arrow-key nudges over the view (0.05 mm, Shift ×10, Page Up/Down lift; one command each), the quick actions, Fit with residuals and a spacing-mismatch explanation, point-to-point picks, Solidcraft's move/rotate triad through a `Proj` adapter with its snap step shown, and markers on leads that miss their lands. The triad keeps Solidcraft's fixed pixel size; Fit view frames the part with a seating plane scaled to it. The lands and the seating plane are a display-only overlay. The placement is a display transform of the built model: a drag or edit never rebuilds geometry, and release sends one command.
- **Tests.** `models/tests.rs` (every family's bodies, materials, lead order and seating; every lead body stands over the core's `lead_points`; parameters; refusals; chunk bounds; reopen in plain Solidcraft; one definition shared by every instance), `models/look.rs`, `package_fit/tests.rs` (fit, quarter turns, mirroring, quick actions, findings), `part_editor/model_tests.rs` (the tab drives one command per gesture and never rebuilds), `viewport/pictures.rs` (the product look drawn offscreen when a GPU is present).
- **Not yet.** Solder fillets for gull-wing, no-lead and header models and for turned chips; edge radii on chip bodies (a native fillet referenced by edge points would not follow the parameters); a mould-texture pattern in the product look (an EDM texture is drawn as the nearest fine grain); a per-draw model matrix in the renderer (a drag repacks the model's vertices on the UI thread, up to `MAX_LIVE_TRIANGLES`, with a notice above it; frame time not yet measured, the 16 ms budget is a target).

## 3D model library, project container and markings (D0–D6 as built)

Track "models" of the [catalog, pins and 3D library work](#catalog-templates-pin-functions-and-3d-library-integration) (founder decisions F5–F7) was built as seven slices on contract commit `3aa006e` and integrated on 1 November 2026. Photoreal appearance comes from GLB materials; STEP carries the mechanical shape with an explicit material mapping; `.solidcraft` stays the parametric native format. Markings are display only.

- **Project container (D0, F5).** A `.pcbcraft` file is a ZIP archive (`crates/io/src/persistence/container.rs`): `project.json` (the editor file, each packed asset's `data` empty) and one raw entry per asset at `assets/sha256/<hash>`; a recovery snapshot adds `recovery.json`. Writes are atomic and reproducible (fixed timestamps, 0644, the document deflated). Reads are bounded on the bytes that actually decompress: 16 MiB document, 64 MiB per asset, 512 MiB per container, 4096 entries (`format::CONTAINER_*`, targets). An unknown, duplicate, directory, link or encrypted entry, another compression method, a missing, unreferenced or mismatched asset, inline asset bytes in `project.json`, a newer version or a pre-container JSON file refuses the file and names the entry. One format version, no migration. The in-memory budget for packed bytes is 96 MiB of base64. `AssetBytes` are immutable and shared (`Arc`): every command's candidate, undo snapshot, save and recovery snapshot shares them instead of copying, and each allocation's SHA-256 is computed once and remembered (a container read hashes each entry once), so revalidating an unchanged asset never hashes it again. Measured: with a 64 MiB model packed, the next library edit took 53 µs (`library_edits_share_and_do_not_rehash_a_large_packed_asset`, macOS arm64, test profile).
- **Model kind (D1, F6).** `Definition::Model(ModelDefinition)` (`library/model3d.rs`) is a revisioned library kind shared by packages, published at rank 2 before packages: one asset (`AssetRef { hash, bytes, media_type, file_name }`, the canonical media type of its `ModelFormat` or `model/gltf+json`), an optional glTF `pair` for a STEP, the `SourceFrame` (unit, up axis, origin offset), bounds, every body mapped explicitly (`ModelBody { key, role, material }`, a built-in `MaterialId` or one of the file's `CustomMaterial`s with PBR factors and KHR clear coat, transmission, IOR and emissive strength), lead tags with their measured contact, an optional marking area, hints (mount, pins, pitch, family) and provenance with redistribution. `PackageModel::Library(LibraryModel { model, lead_map })` names an exact revision and maps lead tags to package terminals explicitly, never by name inference (the UI only proposes exact designation matches). Blocking publish findings: `model.asset`, `model.bounds`, `model.body_unmapped`, `model.leads`, `model.licence`; a package's library model is checked against its terminals (lead map) and, advisory, its envelope. `library.import_model` packs the inline bytes by hash into `Library::assets` and creates a Model draft in one undo step; with `assign: { package, lead_map }` it also sets the new model on that package draft through `library.edit_package`'s path, still one step (the wizard's Finish). Bytes already packed under another media type are refused. A packed asset that no published revision, draft or instance marking names any more is dropped by the `library.edit`, `library.discard_draft` or `library.pack_artwork` that stopped naming it, in the same undo step. Bundles carry a model's assets in records and closures; promote is refused unless redistribution is permitted; update plans list model changes. `library.models { query, fits?, limit? }` searches models with `format:`, `mount:`, `has:leads|marking|textures` and `licence:permitted` facets and, opened from a package, ranks by fit (lead rms or bounds excess) and offers generated families.
- **Import integration (D2).** `crates/solidcraft-integration/src/models/{inspect,imported,gltf_ext}.rs` read STEP AP214/242, GLB/glTF and `.solidcraft` through Solidcraft's public readers. Inspection and build share one reader and key scheme (a body's product path, or mesh name, made unique with `#2`, …), so what the wizard records is what a build rechecks: bounds and every lead contact within 0.01 mm, else the build refuses naming the asset. The frame scales by `unit_mm / format_unit_mm`, turns Y up into Z up and adds the offset (`frame_point`, `frame_bounds`); `reader_frame` leaves the reader's millimetres unchanged. glTF materials are read with `serde_json`, bounded (64 materials); unread look extensions and textures are reported as warnings. Built bodies record role, material and terminal like generated ones; a body with the file's own material is drawn with its full PBR look (clear coat included) and saved as its opaque projection. `library.inspect_model_file` reads a file bounded through io for CLI and MCP.
- **Board and preview.** `project::build` builds a package's library model once per package revision as `pkg<id>r<rev>` (`Builder::library_model`) and places one occurrence per instance like a generated model; a model or asset the project does not hold is refused by the snapshot validation. The Component 3D preview resolves the model (published, or the open draft's pending revision) and its packed bytes on the UI thread only for a new request (`scene::library_asset`) and builds it on the model worker (`imported::preview`). `.solidcraft` models are inspected but not built yet.
- **3D library UI (D3).** The 3D tab's Model section (`model_card.rs`) shows the current model with name, revision, format, licence and lead-map coverage, with Choose model… and Import model file…. The chooser sheet (`model_library.rs`) searches `library.models` with facet chips, a thumbnail grid with the fit score and arrow-key navigation; Enter sends one `library.edit_package { SetModel }`. The import wizard (`model_import.rs`) reads the file off the UI thread, inspects it in the reader frame, and runs File, Frame, Materials, Leads, Licence and Review; suggestions fill a field only when asked and unmapped bodies or unnamed leads block their step. The Leads step shows an estimated contact; Finish measures every contact on the geometry off the UI thread (`imported::lead_contacts`), then sends one `library.import_model` that also assigns the new draft's pending revision with the previewed lead map (one undo step); a refusal returns to Review with the reason.
- **Marking core (D4, F7).** `library/marking.rs` and `marking/{codes,template,layout}.rs`: `MarkingSpec { items, area, finish, min_text_height_mm }` on a component (`ComponentDefinition::marking`) or a Part (`PartDefinition::top_mark`), overridden per instance by `InstanceMarking { hide, vars, replace }` (precedence `effective`: hide, instance, Part, component). Items are text templates over `{mpn}`, `{manufacturer}`, `{designator}`, `{var:…}` and `{field:…|code}`, value codes, SVG artwork by asset hash, polarity marks and colour bands. Codes are pure and never round: 3- and 4-digit resistor codes and IEC 60062 colour bands, EIA-96 over the IEC 60063 E96 series, capacitor pF codes and tantalum voltage letters from a cited table; a value a scheme cannot hold exactly gives no code. `layout` stacks and auto-fits lines in the area and picks the first `Auto` code that fits at the minimum legible height; what cannot be drawn is `marking.unrepresentable` or `marking.does_not_fit` (Info) and draws nothing. `marking.template` blocks publishing. SVG artwork is packed by hash as `image/svg+xml` text of at most 1 MiB by `library.pack_artwork { edits, artwork }` (the marking edit and the files in one undo step) and carries its licence; `marking.artwork` blocks publishing while an artwork is not packed as SVG or has no licence, the snapshot refuses a published marking whose artwork is not packed, `instance.set_marking` refuses a replacing marking with such artwork, and `bundle::named_assets` lists a component marking's and a Part top mark's artwork, so bundles and closures carry it. `instance.set_marking` (one undo step) and the `instance.marking` query (`Option<MarkingLayout>`); `commands::instance_marking` is the same layout as a pure function of a valid project.
- **Marking display (D5).** `crates/solidcraft-integration/src/marking*.rs` turn a layout into a flat mesh 5 µm above the marked face (`DECAL_OFFSET_MM`: at least 32 reversed-float depth steps from the face seen from 1 m, checked in `decals_clear_their_face_in_depth_and_position_precision`): text from Solidcraft's glyph outlines (counters stay open), SVG artwork through the converter, polarity marks and bands; laser etch and white ink draw with their cited materials' looks. Bounded: 65 536 triangles, 32 elements, 64 characters a line, 0.05–50 mm text. On a board the marked face is the outermost flat package face found in the built display geometry; decals are `BodyKind::Marking` display geometry carrying the instance's pick, appended by the model worker (`BoardMarkings`, a per-instance cache keyed by instance, layout hash and area size), never in the native model or fabrication output. The worker reads layouts with `commands::instance_marking` straight from the project (no copy, engine or asset re-hash; 200 marked instances with 64 MiB packed in under 100 ms in `instance_layouts_read_the_project_in_place`); an instance whose marking the core refuses shows none and is reported on stderr. ## Pin functions: peripherals, rules, pinout import and firmware (C1–C7 as built)

1 November 2026. The pins track of the [catalog, pins and 3D library work](#catalog-templates-pin-functions-and-3d-library-integration) is merged (founder decisions F1, F2 and F8). It extends [slice 3](#slice-3--terminal-functions-and-selections) without a second resolution: every rule below feeds the one `functions::resolve` result, and nothing pairs pins, signals or peripherals by name.

- **Pin data (`functions::pin_config`).** A function may carry a mux code (`MuxCode`, ≤ 16 bytes) and a datasheet `SourceSpan`; a terminal may carry a `GpioRef { port, index }` and its settable `PinOption`s (pull, speed, initial level, Schmitt input, each with an allowed list); a resource has a free-text `kind` and a role a datasheet `signal`. These are grouping and display data: `kind` never selects behaviour. `declaration_problems` rejects at publication duplicate GPIOs, repeated or empty option lists, malformed mux codes and empty kinds or signals. An instance stores a `PinConfig` per terminal (`instance.set_pin_config`, ≤ 256 edits, one undo step); `check_config` accepts only options the terminal declares, values in their allowed lists and firmware names that are identifiers of at most 64 bytes. Pin configuration never changes function ERC directly, but pin rules read it through `option(…)`, so a rule can refuse a configuration (`forbid`) or report it unmet (`config.rule_unmet`). It is carried through component updates by `instances` (`config.pin_option` reports a stored option the new revision no longer offers).
- **Pin rules (`functions::rules`, F2).** `ComponentDefinition::pin_rules` holds sandboxed Rhai scripts (≤ 1024 per component, 4 KiB each, 256 KiB in total) next to the typed `Excludes`/`Requires` pairs. A rule reads a typed, read-only `RuleView` (built once, by `rules::view`, for the resolution, the solver and the rule editor alike) through `active`, `active_count`, `function`, `used`, `role`, `kind`, `option`, `excludes` and `requires`, and returns `ok()`, `forbid`, `require` or `warn`; the helper table is in the module documentation. `forbid` is `Conflict::Rule` (rejected), `require` is `Requirement::Rule` (`config.rule_unmet`, blocks Electrically resolved) and `warn` is a `Resolution::notes` entry (`config.rule_note`). Scripts compile once per revision, cached by the hash of their IDs, labels and sources. Limits: 10 000 operations per rule, 1 000 000 per resolution and 20 000 000 per suggestion search, call depth 16, strings 1024 bytes, arrays 1024 items, maps 256 entries, messages 512 bytes; no modules, I/O, time, randomness or `eval`. A compile error, runtime error or exhausted budget is a finding (`rule.script`, `rule.runtime`, `rule.budget`), never a panic; publication also reports `rule.bounds`, `rule.reference` (names checked statically in string literals) and `rule.default_conflict`.
- **Peripheral assignment and the solver.** `instance.assign_peripheral` places each role of one peripheral on a named terminal or lets the solver choose (`terminal: null`), as one `select_functions` batch and one undo step, refused whole when a rule forbids it. `functions.suggest` (`functions::suggest`, adapted by `pins::suggest`) is a deterministic, bounded backtracking search (100 000 nodes, at most 8 suggestions) that ranks complete assignments and otherwise names the blockers, with the first failing rule in `Blocker::rule`; it applies nothing.
- **Pin report (`pins`, module 13a).** `project.pin_report` lists per terminal the pads through the chosen binding, the GPIO, the active function with peripheral, role, signal and mux code, the pin configuration, the net and every other endpoint on that net with its active function, component and MPN. Every placed terminal sits on a net, so an unwired pin has a net of its own and no endpoints. It states facts only.
- **Firmware pin configuration (`firmware`, module 13b, and `pcbcraft-firmware`, F1).** `project.pin_config` turns the report into the format-1 IR: device (designator, component, Part and MPN), the used peripherals with their active roles in declaration order, and one entry per configured pin. A pin's firmware name is its `PinConfig` name, else the name of a net someone named (an unnamed `N<id>` net does not count), else the pin name; clashes are listed in `name_conflicts`, never renamed. `pcbcraft-firmware` (layer 1, core only, no file effects) emits JSON, a C header, a Zephyr devicetree overlay skeleton, Rust constants or a user Rhai template pinned by its SHA-256; the automation requests `firmware.export_preview` and `firmware.export` (new files only) and the CLI `firmware` subcommand write them. The output is a pin-configuration starting point: no clocks, registers or HAL.
- **Datasheet pinout import (`library::pinout`, F8).** A pinout document (format 1, schema from `library.pinout_schema`; ≤ 2048 pins, 256 peripherals, 16 variants, 1024 rules) states device, variants, peripherals with roles, and per row the number in each variant, name, class, GPIO, options, functions with peripheral, role and mux code as separate fields, the default, the source page and an `uncertain` flag. `library.pinout_preview` stages the import on a scratch copy and returns a `PinoutPlan`: a `base` token over the target, the changes (terminals, functions, peripherals, rules, package terminals), review items (uncertain rows, rows that contradict the draft, rows numbered in only some variants) and every publish finding. `library.pinout_apply` takes the plan's `base` (a changed target is refused as a conflict, `pinout.stale_base`) and an `accept` set, and writes one undo step: for a new component the component, a block symbol and a package and binding per variant; for a draft target it matches terminals by number and keeps their IDs. Every written row is recorded as unreviewed in `ComponentDefinition::review` (`pinout.unreviewed`, a warning); a row flagged uncertain blocks publishing (`pinout.uncertain`) until a re-import no longer flags it or a person clears it. The CLI has `pinout preview` and `pinout apply`.
- **Desktop.** The Component workspace's Pins tab (`part_editor/pins_tab.rs`, `pins_table.rs`, `rules_editor.rs`) shows one row per terminal with class, GPIO, function chips tinted by peripheral, pads and the review mark, a peripherals view, the Rhai rule editor with a live syntax check (`rules::syntax_error`) and an explain panel that resolves a scratch selection with the rules folded in, an Unreviewed filter and Paste table, which previews a pasted pinout table through `library.pinout_preview`. In Schematic, the instance card's Pin functions section opens the docked pin-mux panel (`pin_mux.rs`): tick a peripheral to ask `functions.suggest`, cycle the alternatives, adjust pins, see rule explanations inline and a package mini-view, and apply one `instance.assign_peripheral` or `select_functions` batch.
- **Automation.** The EXM-48 scenario (`session/pinout_tests.rs`, `session/firmware_tests.rs`, fixture `mcp/exm48.pinout.json`, an invented single-package controller) runs JSON-only through schema → preview → stale-base refusal → apply → undo/redo → the F8 gate → corrected re-import → review confirmation → publish and place → suggest → assign (explicit and solver-placed) → a rule-forbidden assignment refused → pin configuration → wire and name a net → pin report → IR → every emitter → export to a new file, with the footprint and model step of [the integration](#catalog-templates-pin-functions-and-3d-library-integration) between review and publish. The MCP instructions describe the same reviewed workflow. The core's import tests use a separate two-package fixture, EXL-48.

### Spec ambiguities resolved

1. **Binding pin direction.** Component pins bindings; bindings record component lineage ([section (a)](#reference-graph-acyclic)).
2. **Footprint choice.** A binding lists allowed footprint variants of its package revision. The instance chooses a binding and one of its footprints by lineage.
3. **ID form.** Typed numeric local IDs replace the spec's illustrative string IDs. `FunctionId` is component-scoped; a `FunctionKey` must pair it with its own terminal.
4. **CE-04 "unplace an unwired unit".** The proof disconnects B first through ordinary commands.
5. **CE-06 open-drain alternative.** It is on terminal 3, not terminal 1, so the open-drain ERC proof uses terminal 3.
6. **Decisions for unused-unit terminals.** These are project no-connect markers on the instance. No-connect never satisfies a required power input.
7. **Wiring an unplaced unit.** It is impossible: a wire endpoint requires its unit to be placed. Unplacing a wired unit goes through the planner.
8. **"Accounted for".** A terminal is accounted for when it is connected (net size ≥ 2) or marked project no-connect (`nets::accounted_for`). Device-NC and reserved terminals need nothing.
9. **Conflicts versus incompleteness.** Capacity, exclusion and availability conflicts are rejected invariants. A missing prerequisite or required role is a finding, so stepwise edits remain possible.
10. **Unused versus placed.** They are exclusive. Placing an unused unit is rejected until the flag is cleared.
11. **NC level.** Device NC is classified on the component terminal. Package-level non-electrical terminals and holes are CE-07.
12. **Purchasing state.** Not computed in these slices, and reported as not computed.
13. **Bare prefix and parse precedence** for `10k` / `10m`, as specified in slice 2.
14. **File version.** It stays 1. Older development files are refused as malformed.
15. **`component.new`.** Served by `library.new_draft` with a component body.
16. **Symbol reuse.** Symbols are owned by one component lineage in these slices ([open questions](#open-questions-and-deferrals)).

## (g) Test plan

Expected values are hand-derived from the synthetic fixtures above. Tests drive public commands and queries (`Engine::apply`, `Engine::query`, `Session::dispatch`) and assert observable state. Implementation details are not asserted.

### Slice 1

- **Publication:**
  - Atomic five-definition publish.
  - Any single blocking finding publishes nothing, and revision, history and drafts are unchanged. Cases: missing mapping; a pin for an unknown terminal; a binding of another lineage; a footprint of another package revision; a dangling reference; a reused retired ID; a local ID at or above the revision's own `next_local`; a component listing two revisions of one symbol lineage; a component listing two revisions of one binding lineage; a binding listing two revisions of one footprint lineage.
  - A stale base gives `conflict`.
  - Decode rejects a file whose published revision has a `Publish`-blocking finding, and reopens one whose revision has only advisory findings.
- **Drafts:**
  - An empty component draft and a contradictory finite draft survive `encode`/`decode` and the recovery round trip unchanged.
  - NaN and oversize drafts are rejected.
  - `component.check` with `Draft` and with `Revision` targets reports the findings of exactly that target, with `blocks`, and nothing is stored as a stamp.
- **Staged completion:**
  - A component published with no implementations can be placed.
  - `layout.sync` skips it, with finding `instance.no_physical_choice` blocking `BoardPlaceable`.
- **CE-04 and CE-05:** the walk-throughs above, with exact counts, IDs, positions and finding sets. Undo/redo of each mutation, and save/reopen equality of all IDs, pins, unit states and markers.
- **Ported update tests:** the existing `updates/tests.rs` cases (geometry change preserves copper, mapping change lists track removal, label-only warning, unrelated definition blocked, locked copper, newly device-NC). Also a choice that is no longer offered, blocked until a resolution is supplied.
- **Unit resolution:** a representation-lineage change is blocked for an instance with an occurrence and for one with only an `unused_units` entry, even when the target symbol has a unit with the same numeric ID; each applies with explicit `UnitResolution`s. A same-lineage revision removing an unused unit lists the flag's removal without blocking.
- **Regroup:** a terminal moved into an unplaced unit while wired blocks the plan; each `RegroupAction` applies with the expected wires and occurrences.
- **Atomic failure and history:** stale revision, malformed JSON and unknown IDs on every new command leave revision and history unchanged.
- **ERC port:** the existing unconnected-input test becomes a completeness test asserting `instance.terminal_unaccounted` and no `erc.*` finding for the lone terminal.
- **Transport:**
  - The session test places a component and inspects it through JSON.
  - `schemas()` includes the new operations, `Query` and `EditorFile.drafts`.
  - MCP `tools/list` includes `project_query`, which carries `component.inspect`, `component.check` and `component.check_drafts`.
  - The CLI and MCP results, including query reports, equal the direct engine result for the same request sequence.
- **Native integration:** the existing native build and regeneration tests are ported to resolved definitions, and the package-preview test is updated.
- **Desktop:** the existing editor unit tests are ported (commit once, template load is undoable, draft edits keep the board model key). Manual inspection confirms unchanged capability. This is not CE-C1 evidence.

### Slice 2

- **Quantity:** the moved tests still pass. `scripting` tests pass against `crate::quantity` with `Script.units` ported to `UnitSet`; no `UnitDefinition` remains.
- **Parsing:**
  - `10k`, `10 kΩ` and `10000 Ω` give `si = 10000`.
  - `10 µF` on resistance is rejected, and the committed value, revision and history are unchanged.
  - `0` gives `Assigned(0)` with `origin = Assigned`, distinct from `Unset` (`origin = ExplicitlyUnset`) and from `Inherit` (`origin = ComponentDefault`).
  - Bounds, unknown enum choice and text length are rejected.
- **Tolerance:** `±5%` is minus = plus = 0.05. `−20%/+80%` on 10 µF gives the interval 8 µF – 18 µF.
- **Kind identity:** two kinds with equal dimension are not interchangeable. A field revision that changes its kind blocks the update until a `FieldResolution` is supplied.
- **Independence and persistence:**
  - Two instances have independent overrides.
  - A field label change keeps the assignment.
  - Save/reopen preserves `si`, `display_unit` and origin.
  - Undo/redo of the batch.
- **Required fields:** a missing required field blocks `ElectricallyResolved`.
- **Transport:** `instance.set_properties` via the session returns the same `effective` values as the engine.

### Slice 3

- **Publication:** rejects `Input`+`PushPull`, `Output`+`None`, `Power` signal with a non-power direction, duplicate function IDs, a `design_default` not in the list, an unknown resource or role, `DeviceNc` with functions, a `FunctionKey` whose function belongs to another terminal, design defaults that together exceed a role's capacity, and a binding marking a fixed function or design default unavailable.
- **CE-06 cases:** every row above with the exact finding codes and objects.
- **Capacity rejection** leaves revision and history unchanged. The ordered batch move is one revision step and one undo step.
- **Update preview:** reorder/rename is retained, and removal is blocked until resolved.
- **Availability:** rejected for direct `set_physical`, blocked in the plan, and never reported as a `BoardPlaceable` finding.
- **Wiring rules:**
  - A device-NC terminal cannot be wired.
  - A project no-connect cannot be set on device-NC.
  - A wired terminal cannot be marked no-connect, and a no-connect terminal cannot be wired; both are rejected with the same `instances::check_instance` diagnostic.
- **ERC baseline:** passive-only nets produce no findings. An unresolved terminal gives `erc.unchecked_terminal`.
- **Persistence:** save/reopen preserves arrays, IDs and selections. The JSON schema exposes the structured function arrays.

## Open questions and deferrals

| Item | Status | Owner |
| --- | --- | --- |
| Cross-component symbol reuse | Deferred. Symbols and bindings belong to one component lineage, so the spec's "reuse an existing symbol where suitable" is narrowed to reuse within a lineage and to forking. Sharing a symbol between components needs a terminal-mapping layer between the symbol's pins and each component's terminals, with its own update rules. No accepted scenario requires it. | Revisit with `library.duplicate` (CE-01) or shared library folders |
| Collision-free `DefinitionId`s across projects | Deferred. The opaque newtype keeps the representation replaceable. | Shared library folders |
| Intra-crate module dependency table | Not enforced by `cargo xtask layers`, which checks crates. Until a module-level check exists, the [module map](#d-module-map) is a reviewed contract. A follow-up could extend `xtask layers` to reject `use crate::` edges outside the table. | Slice 1 review |
