# Parts library

Design, decisions and slice plan, 30 October 2026. Condensed from the reviewed design proposal. **Slice S1 is implemented** (see [S1 as built](#s1-as-built)). **Slice S2 is implemented** (see [S2 as built](#s2-as-built)). **Slice S3 is implemented** (see [S3 as built](#s3-as-built)); S4–S5 are plans. Package rows, the Model kind and pin data were added on 1 November 2026 (see [package rows, pin functions and 3D models](#package-rows-pin-functions-and-3d-models)). Every estimate and performance figure is labelled a target, an estimate or a measurement. Nothing here is legal advice.

## Summary

Pcbcraft already has immutable revisions, exact references, drafts, publish cascades and reviewed updates ([component model](component-model.md), [part library design](part-library-design.md)). The parts library adds a **catalog layer** around that core:

- **Sources:** the project snapshot, later also local library folders shared as plain files or git.
- **A manufacturer-part record** (`Part`) next to the generic component.
- **Labels for finding things** that never act as identity: shelves, tags and data-derived facets.
- **One unit-aware search function in the core.** The Place palette, the Browser, the CLI and MCP all call it.

Placing from a library copies the full dependency closure into the project in the same undoable transaction. The project never resolves anything through a folder or index, so it still reopens offline.

## Data tiers

| Tier | What it is | Authority | Where it lives |
| --- | --- | --- | --- |
| Project snapshot | Every revision the project references, with its closure and asset bytes | Authoritative for the design | `Project.library` |
| Library sources (S3) | Local folders of immutable revisions, read-only or writable | Authoritative for new imports only | On disk, listed in per-user settings (io) |
| External catalogs (S5) | Optional supplier connectors returning observations | Never authoritative; expires; never shared | Per-user cache only |

## Library items

A Library row is a **lineage**: one identity with many immutable revisions.

- **Component lineage** (exists): the generic electrical interface with its symbols and bindings.
- **Package and footprint variants** (exist).
- **Package row** and **Model** (exist): a cited package form a template builds from, and a 3D model file shared by packages; both are revisioned kinds published before packages.
- **`Part`** (S2): a revisioned lineage holding the manufacturer, the complete MPN, a pinned `ComponentRef` and `BindingRef`, rated specs as typed field values with a comparison meaning, references and provenance. The publish cascade grows to footprint → binding → component → Part. An instance's `PartRef` must agree with its own component and physical choice; a component update that leaves a Part pinned to the old revision raises a finding and an update choice and is never re-pointed silently. An "atomic part" in other tools is a component plus exactly one Part.
- **Reference** (S2): datasheet or application note link with stable local ID, kind, title, URL, optional document revision, optional asset hash, licence and provenance. A link is not a copy.
- **Distributor offer** (S2): distributor name, SKU, product URL, optional packaging. No price or stock.
- **Lifecycle observation** (S4): normalised status, the source's raw label, source, observed-on date and optional last-buy date. Authored or imported by the user; it never changes existing designs.

**Generic first, exact later.** An instance keeps its typed requirements and may also pin an optional `PartRef` (on `model::ComponentInstance`; rules in `instances`). One pure predicate, `fields::satisfies(requirement, spec)`, compares them by declared meaning (exact nominal, minimum rating, maximum tolerance) and is shared by search, `instance.assign_part` and purchasing completeness.

**Organisation without identity.** A *shelf* is an optional shallow path label; *tags* are free-form user labels; *facets* are derived from the fields the results carry. No category is hard-coded, and no vendor, EDA, IEC CDD or ECLASS taxonomy is copied. Shelves and tags live with the source that owns the lineage, outside revision identity (D13).

**Health** (S4) is derived like completeness, never stored: missing footprint, binding or model; unmapped terminals; no Part; unknown provenance or licence; no review record; risky lifecycle ("today" is an input); duplicate MPNs; a newer revision in the source. It is a filter and a report, never a gate.

**Provenance** (S2) becomes structured: `origin` (library, source lineage, revision, content hash), `basis` (authored, from a reference, imported), licence and the existing free-text note.

## Query language

`parse_query(text, &Vocabulary) -> Result<CatalogQuery, QueryError>`. Input is at most 512 bytes and 16 terms. Terms are ANDed.

- **Free text** matches names, descriptions, package labels and field texts, case-folded. `"…"` keeps spaces and is always text.
- **Reserved filters:** `pkg:` (a text match on package names only; it implies nothing about compatibility), `has:` and `missing:` (`symbol`, `footprint`, `3d`, `mpn`), `src:project` and `kind:component` (the only entry kind in S1, so it keeps every entry). `implements:12/3` keeps the project Parts that pin exactly that component revision and `implements:12` those pinning any revision of that lineage: identity, never a name, and a folder entry's catalog-local ids never match. `tag:`, `shelf:`, `mpn:` and `life:` are reserved and report that their data does not exist yet. Reserved keys are checked first, so a field named `Kind` or `Life` is reached through a shorter prefix of its name (`kin:`, `lif:`); an unknown-key message lists the fields and the reserved filters.
- **Field predicates:** `key op value` with `>= <= > < = :` and ranges `key:min..max`. Keys are data, resolved in an order that never depends on which other fields exist: a key that spells a unit symbol or alias of any field's quantity kind (`V`, `kV`, `Ω`, `ohm`, `R` where the data declares it) is always a **unit key** and names every field measured in that unit; any other key is a field name, exact or a unique prefix (`res`, `tol`, `volt`). The code holds no field names, units or category branches. An ambiguous prefix or an unknown key is an error that lists the fields.
- **Values** are read by `quantity::parse` against the field's own unit set, after an **RKM pre-pass**: a letter used as the decimal point becomes a decimal (`4k7` → `4.7k`, `2u2`, `4R7`, `R47`). Multiplier letters are the one-letter SI prefixes; unit letters are the one-letter symbols and aliases of the field's unit set, so `R` is a decimal point only where the data declares `R` (as the synthetic resistance kind does).
- **Dimension check:** a unit key filters every field measured in that unit, so its value is a plain number in the key's unit (`V>=25`) or states a unit of the same kind (`V>=0.025kV`). A bare multiplier after a unit key is always refused instead of being guessed: `V>=10k: 10 k has no unit of voltage`, and, where the data declares `R` as an alias of Ω, `R>=10k: 10 k has no unit of resistance` (write `R>=10kΩ` or `res>=10k`). After a field-name key a bare multiplier reads in the default unit, as in property entry (`res>=10k`, `volt>=10k`). Adding or renaming a field never changes what a unit key means.
- **Meaning:** comparisons "meet", not "equal". `tol<=1%` matches ±0.5 % and ±1 % (each side compared). A range field reaches a bound (`≥` its maximum, `≤` its minimum) and covers a `min..max` predicate. Quantity equality allows a relative 1e-9.
- **Bare values** with a letter (`10k`, `4k7`, `100nF`) are tried against every quantity field they read as, and as text; the chip shows each reading. Plain numbers such as `0603` stay text.

## Ranking

1. **Match tier**, worst over the text terms: exact name or lineage ID, name prefix, whole word, substring (name, description, package), field value only. A query of filters only ranks every match equally.
2. **Boosts:** used in this project, favourite, recently used (most recent first). Favourites and recents are inputs (`CatalogContext`); the core reads no settings.
3. **Final ties:** folded name, source, lineage ID.

Equal inputs always give the same order, whatever the entry order. Hidden entries are counted by reason ("1 hidden (unpublished draft)"), never dropped silently. Stock or price never reorders results.

## Package rows, pin functions and 3D models

1 November 2026. The catalog, templates, pin functions and 3D library work ([integration](component-model.md#catalog-templates-pin-functions-and-3d-library-integration)) adds two library kinds and pin data, all ordinary revisioned definitions that bundles, imports and the D1 ref rewrite carry like the rest:

- **Package rows** (`PackageRowDefinition`): one typed package form of one of eight families, with aliases, a size code, optional cited lands and a per-row citation or none (*estimated*). `library.templates` searches project rows, every loaded source's rows, 196 built-in starter rows and each family's custom entry with `pins:`, `pitch:`, `body:` and the size-code rule. A folder row is read with its bundle and carried inline; a row is never resolved through a folder after the build ([libui as built](component-model.md#component-workspace-catalog-and-package-templates-libui-as-built)).
- **Models** (`ModelDefinition`): a GLB, STEP or `.solidcraft` asset packed by hash, its frame, bodies mapped to materials, lead tags and licence. `library.models` searches them with the generated families and ranks by fit to a package; a package names an exact revision with an explicit lead map ([D0–D6 as built](component-model.md#3d-model-library-project-container-and-markings-d0d6-as-built)). Its redistribution field travels with the model into folders.
- **Pin data** on components (peripherals with kinds and signals, mux codes, GPIO, pin options and Rhai pin rules) is part of the component revision, so it is part of snapshot identity and of the impact preview of a library update; per-instance pin configuration is carried through updates and an update lists the configurations it drops ([pins as built](component-model.md#pin-functions-peripherals-rules-pinout-import-and-firmware-c1c7-as-built)).

## S3 as built

31 October 2026. S3 was built as four parallel tasks over one up-front contract of types and stubs, then integrated: (1) core import, export, duplicate, the reference-rewrite visitor and source catalogs; (2) io folders, the index cache and settings; (3) desktop sources, Place palette and promote; (4) automation, CLI and docs. The contract note was removed once this section described the result. Decisions in force: D1 (remap on import with a recorded origin; random 128-bit ids inside folders), D2 (the folder format below), D7 (asset bytes packed into the project file by content hash) and D13 (shelves and tags in the folder's `catalog.json`). One format version, no migration.

**Folder format (io, `library_folder`).** `pcbcraft-library.json` (`format` 1, `library`, `name`, `required_features`, `default_licence`); `lineages/<lineage>/rNNNN.json`, each exactly one core `RevisionRecord` (`lineage`, `revision`, `kind`, `meta`, `definition` with record-local ids, `links` from those ids to source lineages, `assets`), never overwritten with other content; `assets/sha256/<hash>`; mutable `catalog.json` labels. Output is pretty JSON with a final newline and stable key order. A manifest of another format or with an unknown required feature is refused as `unsupported` (the version and features are read from a lenient probe first, so a newer format that adds fields is still reported as unsupported, not unreadable); a malformed one is `invalid_input`; each is listed with its reason (`Disabled`) rather than dropped. `read_bundle` reads only the closure: it follows links from the root, reads each `rNNNN.json` when first reached and lists a lineage directory only for a soft dependency's latest revision; the desktop runs it on a worker. Library and lineage ids come from the operating system's random source in io, unless a recorded session supplies them; the core never generates them.

**Identity and import (core, `library::bundle`, `library::import`).** `Origin { library, lineage, revision, content_hash }` (SHA-256 of the record's canonical JSON) and `OriginRecord { local, origin, direction }` (`imported` or `promoted`) live in `Library.origins`, outside revision bodies; `PackedAsset`s live in `Library.assets`. A `Bundle` carries a root revision with its closure, dependencies first, inline in `library.import` and `library.place_from`, so replay stays deterministic. Import dedupes by origin, maps each new source lineage to a fresh project lineage and each newer source revision of a known lineage to that lineage's next project revision, rewrites every reference through the one visitor (`rewrite_refs`) and packs assets. Because project revisions are numbered in import order, a source revision older than one already copied of the same source lineage is refused (`conflict`, `library.older_revision`), directly, as Keep both or as a dependency, so the project's latest revision is always its newest source revision; import the newer revision, or update what pins the older one in the library. A bundle whose revisions are all in the project already changes nothing (no revision, no undo step). Packed assets are bounded at 8 MiB each and 11 MiB of base64 in total per bundle and per project (`MAX_PACKED_BYTES`), so an import never leaves a project too large for the 16 MiB file bound. `export` (promote) is pure: members whose origin is already in the target map back to their source lineage, new ones take ids from the io-drawn `fresh` list in order. `duplicate` (D6) copies a component with its symbols and bindings into new drafts. In S3 the duplicate records its source only as text in `DefinitionMeta::provenance` ("Duplicated from ‘…’ (Dn rN).") on each copy; a typed duplicate-of `DefinitionRef` carried into publication is planned with structured provenance for every kind (S4), so tools cannot yet trace a duplicate by type.

**Commands and queries.** Core operations `library.import`, `library.place_from` (import if needed and place, one undo step; another project revision of the root's lineage is refused with `library.other_revision` unless `other_revision` is `keep_both`), `library.promote` and `library.duplicate`; queries `library.promote_preview` and `library.updates_available` (copies whose source holds a newer revision, or whose recorded records no longer hash to their origins: `modified` lists those source revisions, finding `library.source_modified` names them). `library.search` and `library.facets` search the project and every ready source (`Index::with_sources`); folder entries carry `source: {library}` and `source_lineage`, and are placed through `library.place_from`.

**Importing from another project file (gap 4 of the [end-to-end run](e2e-esp32-devboard.md)).** The session request `library.import_from_project { expected_revision, path, root }` reads the `.pcbcraft` file (never changing it), builds a bundle of one published revision and its closure with `library::import::project_bundle`, and applies one ordinary `library.import`, so it is one undo step, with the bundle inline and the same dedupe, refusals and packed assets. A project file has no identity that survives editing, copying or moving it, so no path, name or file hash is used. Every copy names one reserved origin library (`import::PROJECT_FILES`), and a lineage's source id is the hash of its id, kind and immutable first revision (`import::project_lineage_id`). Consequently: the origin keeps the exact source revision number while the project numbers its copies in import order (D1); importing again reuses the copies with no undo step; a newer revision of the lineage, from the same file edited or moved, becomes the same project lineage's next revision; two files that disagree about one revision are refused (`library.source_modified`); and ids need no random source, so a replay is reproducible. A draft in the file is refused by name: only a published revision is immutable, so publish it there first. A model whose licence forbids redistribution is refused as for a promote. Limits: a part the file itself imported from a folder or another file is treated as that file's own, so it does not dedupe against a copy from the original source; there is no desktop command yet.

**Reproducible folder ids.** Folder ids stay random by default (D1). For a replay, the caller supplies them: `library.source.create { library }` (`library_folder::create_folder_as`) and `library.publish_to_folder { fresh }` take the ids the session recorded, and the plain JSON-lines replay then rebuilds equal records and origins. Recorded ids in the requests were chosen over a replayer that maps old ids to new ones because replays are plain lines fed to `pcbcraft-cli stdio` and no stateful replayer exists. `fresh` is consumed in closure order; too few refuses before anything is written. The id `import::PROJECT_FILES` is refused for a folder.

**Index cache and settings (io).** `<cache>/index/<library>.json` holds the manifest hash, each record's hash and the `SourceCatalog`; any mismatch rebuilds the whole index from every record, and a deleted index rebuilds identically. A cache file that cannot be written (an index over the 16 MiB file bound, an unwritable cache directory) is not an error: the catalog is used from memory (`IndexState::Uncached`) and rebuilt on the next scan. `settings.json` in the user config directory holds the sources (`path`, `enabled`, `writable`, and the manifest `name` last seen, so a missing folder is still listed as its library), favourites and recents keyed by `EntryKey::Library` (library id and source lineage), never by path or name, and never in a project. A project lineage id names something else in every project, so settings refuse `EntryKey::Project`; a project copy of a folder item is remembered by its origin (`CatalogEntry::user_key`, and `CatalogEntry::origin` in every project entry), and a project-only item's marks rank for the open project only. `PCBCRAFT_CONFIG_DIR` and `PCBCRAFT_CACHE_DIR` override the platform directories. Only a missing `settings.json` means defaults. A file that exists but cannot be read (a permission error, a bad byte, another format) is refused and never saved over: the app reports it and runs on defaults for that session, and the CLI and MCP session refuse source changes rather than keep them in memory.

**Desktop.** The Browser lists every configured source under "Library sources", a disabled one dimmed with its reason, and a Manage sources… card that adds a folder, makes a new library, rescans, turns sources on or off, marks them writable and shows a folder in the file manager (the path is its tooltip). The card is also File › Library sources… and the Place palette's Library sources… button; ⌘B, the app bar's Browser button and File › Show Browser toggle the Browser, which floats over the canvas when the window is too narrow to dock it. Components the source has moved on show "rN · rM available" with an update icon in the Browser, and instances pinned to an older revision than the project or a source holds are marked there too. Folders are opened (`library_folder::inspect_folder`, the same typed `Disabled` reasons automation reports) and indexed on a background thread; each scan carries a ticket so an older scan never replaces a newer one, and one writer thread saves the settings in order. The Place palette lists folder entries under "LIBRARY · <name>" after the project's; a project copy whose source moved on carries an "Update rN" chip (or "rN changed" in the warning colour for a modified record, naming that revision), a favourite a star, and the project and folder rows of one lineage name each other ("from Sample Parts", "in project r1") with usage per revision. Enter or a click reads the bundle on a worker and sends `library.place_from` at the free grid point nearest the view centre, inside the view; the new instance is selected and brought into view. A `library.other_revision` refusal ("This project uses … r1 from Sample Parts; the library now has r2.") reopens the sheet on an inline Update project copy… (the default, Enter) / Keep both / Cancel choice. Update is `library.import`, then the update review with a checkbox per instance and a note that the revision was copied in; Cancel undoes the import. The Properties preview of an out-of-date project row says "r1 · r2 available in Sample Parts" with Update…, and a Schematic instance on an older revision has an "rN available" row with Update…, which reviews that instance only. Cmd+D toggles a favourite; assign mode lists no folder entries. The Component workspace gains a Library section (origin, "Copied from" or "Published to", Promote to library…, Duplicate): promote previews with `library.promote_preview`, listing every record it writes or finds already in the library, writes with io's `write_bundle` off the UI thread and records the origins with `library.promote` at the previewed revision; duplicate runs `library.duplicate` and opens the copy.

**Automation and CLI.** `session::sources::Sources` is the session's source registry; with `UserDirs` it reads and writes the user's settings and caches indexes, otherwise it keeps sources in memory and builds catalogs from the records. `project.query` passes its favourites, recents and ready catalogs to the core as `CatalogContext`. Session requests, each with a generated schema and MCP tool: `library.sources`, `library.source.add` / `create` / `remove` / `enable`, `library.rescan`, `library.favourite`, `library.bundle`, `library.import_from_folder` and `library.place_from_folder` (read a folder bundle, then apply exactly one core `library.import` / `library.place_from`; placing records a recent) and `library.publish_to_folder` (the three promote steps: `library.promote_preview` with fresh random ids, io writes the bundle, then `library.promote` with the ids the plan used records the origins as one undo step; the revision is checked before anything is written). A failed source request changes neither the settings nor the document; once a placement is applied, a recents write that fails is reported in the reply's `warnings`, never as an error. Favourites and recents name library items only (`EntryKey::Library`); a project lineage id means something else in every project and is refused. The CLI's `stdio` and `mcp` sessions use the user's sources; `pcbcraft-cli sample-library NEW_DIR [NAME]` writes the synthetic catalog (components, generic components and invented `ExampleCo` Parts) as a new folder through `session::publish_library`, without touching the user's settings.

**Evidence.** The scenario (install a folder, place R1 and R2 from it, publish r+1 in the folder from the authoring project, update only R1, detect a modified rN through `updates_available`, delete the folder, reopen offline with both revisions and their origins) is the JSON-only automation test `install_place_publish_update_delete_and_reopen_offline`. Refused manifests (missing, other format, unknown feature, malformed, turned off), persistent favourites and refused publishes run over JSON too. Manifest refusal, hash detection of a modified rN and identical index rebuild are io tests; the import/export round-trip property test is a core test. See [editor evidence](editor-evidence.md#parts-library-s3) for what has run.

**Not in S3.** Shelf and tag editing and the Library workspace (S4), `library.prune`, network sources and connectors (S5), and merging two folders that hold the same library id (`library.source.add` refuses the second; one configured by hand is listed as failed and not searched, in the desktop and in automation alike).

## S2 as built

31 October 2026. S2 was built as three parallel tasks over one up-front contract of types and stubs (core rules, desktop UI, automation and docs) and integrated in one merge; the contract note was removed once this section described the result. One format version, no migration: `Library.parts` and `ComponentInstance.part` are `serde(default)` and skipped when empty, so files without Parts are unchanged.

**Types (core).**

- `ids`: `DefinitionKind::Part` (last variant) and `PartRef { id, revision }`.
- `library::part`: `PartDefinition { next_local, manufacturer, mpn, component: ComponentRef, binding: BindingRef, specs: Vec<RatedSpec>, references: Vec<Reference>, offers: Vec<DistributorOffer>, provenance: Provenance }`, stored as `Definition::Part(Box<PartDefinition>)` (boxed for size; serde does not see the box) in `Library.parts`, with `Library::part` and `Library::latest_parts`. References and offers share `next_local` under the usual retire rules. Bounds: 64 rated specs, 32 references, 32 offers, 2048-byte URLs, `MAX_LABEL` text and 64-byte hashes.
- `Reference { id, kind: datasheet | application_note | other, title, url?, document_revision?, asset? (SHA-256 hex), licence?, provenance }`. A link is not a copy; `asset` names the attached copy. `DistributorOffer { id, distributor, sku, url?, packaging? }`, part of the Part revision (D3), with no price or stock (D9).
- `Provenance { origin?: Origin { library, lineage, revision, content_hash }, basis: authored | from_reference(id) | imported, licence? }` (D1; `library` is text until S3 defines library identity). The free-text note stays in `DefinitionMeta::provenance` for every kind; moving the other kinds to structured provenance is outside S2.
- `fields::spec`: `RatedSpec { field, value, meaning }`, `SpecMeaning` (`exact_nominal`, `minimum_rating`, `maximum_tolerance`), `Requirement { field, label, value, value_type, nominal? }` and the pure `satisfies(requirement, spec) -> Vec<Finding>` (empty means it meets the requirement) with the codes `part.spec_mismatch`, `part.spec_field_mismatch` and `part.spec_uncomparable`.
- `ComponentInstance.part: Option<PartRef>`; the one invariant (shared by commands and decode) is that a pinned Part resolves in the project library. Disagreement with the instance is a finding, never an invariant.
- `completeness::purchasing`: `PurchasingReport { state: no_part | unresolved | resolved, part, manufacturer, mpn, findings }` on `InstanceReport.purchasing` (findings advisory, not repeated in `InstanceReport.findings`); `BomReport { lines: Vec<BomLine>, unresolved }` and `ResolveReport { groups: Vec<ResolveGroup> }`.

**Rules (core).**

- **Comparison.** `ExactNominal` on quantities (relative 1e-9), integers, booleans, enums and text; `MinimumRating` on quantities, integers and ranges (a rated range must cover the required one); `MaximumTolerance` on each side of a tolerance. `ExactNominal` on a range means equal ends. Tolerances of different bases are compared as intervals around the requirement's `nominal` through `tolerance_interval`; absolute bases of different quantity-kind lineages, or a missing nominal, give `part.spec_uncomparable`. A spec is read in its own field revision's value type.
- **Publish.** `publish_rank` 7, after components, so one `library.publish` set publishes footprint → binding → component → Part atomically. Findings: `part.identity` (manufacturer or MPN not printable), `reference.missing` (pinned component, binding or a spec's field absent), `part.binding_unlisted` (the component revision does not list the binding), `part.spec_field` (the component does not select the field), `part.spec_duplicate` (one spec per lineage), `part.spec_value`, `part.spec_meaning` (meaning must fit the value type), `part.reference_text`, `part.offer_text`, `part.link` (http(s) only), `part.hash` (SHA-256 hex) and `part.provenance_basis` (a `from_reference` basis names an existing reference).
- **Instances.** `instances::requirements` lists every selected field with an effective value; a tolerance carries the nominal of the one selected quantity field in the absolute basis's quantity kind. `part_findings` reports `part.component_mismatch`, `part.binding_mismatch`, `part.stale_component`, `part.newer_component` (the Part is for a newer revision of the instance's component), `part.spec_unrated` (a requirement the Part does not rate is never an implicit pass) and every `satisfies` code. `instance.assign_part` (1–256 instances) is atomic: the Part must pin each instance's component revision and the binding of its physical choice and rate and satisfy every requirement, otherwise `conflict` naming the field and nothing changes; `None` clears. One Resolve-parts group is one command and one undo step.
- **Updates.** `Resolutions.parts: Vec<PartResolution { instance, action: keep | clear | assign { part } }>`. Without an entry the instance keeps its Part, which then pins the old component revision: the preview and purchasing report `part.stale_component` and purchasing stays unresolved. The Part is never re-pointed. `assign` sets a Part together with the revision update (how a Part published for a newer component revision is assigned in one previewed transaction); it refuses the whole update unless the Part agrees with the instance at the target revision. Finding messages name components by name and revision and bindings by name, never by definition id alone.
- **Purchasing, BOM and Resolve.** `resolved` needs a Part with no purchasing finding. `project.bom` groups resolved instances by Part and the rest by component revision, footprint and identical requirements, marking each line `unresolved` when it has no Part or its Part has a finding. `library.resolve_groups` lists the unresolved groups in BOM order, each with the `library.search` text (`kind:part`, `implements:` the group's exact component revision, and the requirements as field predicates) that finds Parts for it, so a component without fields never matches every Part. The Choose… palette reads that term as the whole lineage, so a Part for a newer revision is still listed, flagged, with the reviewed update-and-assign.
- **Catalog.** Parts are indexed as `CatalogEntry.kind = Part` with manufacturer, MPN and spec values; components with a Part carry the MPN badge; `kind:part` / `kind:component` filter and `mpn:` matches the MPN only; an equality predicate on a Part's rated value is decided by `fields::satisfies` (so search, assignment and purchasing agree), while explicit `<`, `≤`, `≥`, `>` keep their literal meaning. `CatalogEntry::component()` stays component-only. `catalog::synthetic` adds original ExampleCo Parts (`EX-R0603-10K0-F`, `EX-R0603-22K0-F`, `EX-C0402-100N-25V`) pinning two generic components.

**Desktop.**

- **Component workspace, Parts section** (`part_editor/part_props.rs`): lists the lineage's Part drafts and published Parts and edits one draft through the form kit: maker and MPN (the draft's name follows the MPN), rated values typed through `fields::parse_value` with a meaning limited to those that fit the value type, references (kind, title, link, document revision, licence, attached copy hash), distributor offers (identity only) and structured provenance. New Part, Edit, Discard and Publish are library commands. With unpublished component edits, Part drafts retarget to the pending revisions and publish in the one cascade set; unfinished Part and working-set edits travel in one `library.edit`, so neither reload drops the other.
- **Schematic properties:** a Part section on the instance with Choose… (the Place palette in assign mode, pre-filled with the group's query or `kind:part`; Enter sends `instance.assign_part`) and Clear.
- **Review fixes.** Assign mode lists only Parts of the instances' component lineage; a Part for a newer component revision is flagged on its row and Enter opens the update review with `PartAction::Assign` (update and assign in one step). In Place mode components rank first and Enter on a Part row explains that Parts are assigned, not placed. A rated value added without a default is a pending row until a value is typed; findings wait until an identity is typed or Publish is pressed. Resolve groups show the current Part and its findings, and New Part… (also in an empty assign search) opens the component's Parts editor with a draft rated at the group's values. Unresolved BOM lines lead with their state in the warning tone. The Browser lists Parts under their component and marks instances whose Part disagrees; Check lists purchasing findings; a property edit that contradicts the pinned Part is hinted before Apply. Not yet: a canvas marker, attaching a file by picking it (the hash is typed), and shortcut routing while the pointer is over Properties.
- **Resolve parts** (ribbon Resolve, `resolve_parts.rs`): a card over `library.resolve_groups` and `project.bom` with one Choose… per group, sent as one `instance.assign_part`, and the BOM lines with unresolved ones marked. It states when every instance has an agreeing Part.

**Automation.** CLI `stdio` and MCP reach `instance.assign_part` through `project.apply` and both queries through `project.query`, with generated schemas; the MCP instructions describe the Resolve-parts workflow. JSON-only tests author and publish an ExampleCo Part (`library.new_draft`, `library.edit`, `library.publish`) mirrored on a directly driven engine, keep a URL-less reference and its attached copy through save and reopen (CE-07), run Resolve parts → one group assignment and one undo step → `purchasing.state` `resolved` → a BOM with no unresolved lines (each report equal to the engine's own query), and refuse an empty instance set or an unknown Part without changes.

## S1 as built

**Core (`pcbcraft-core::catalog`, module-map row 14).** Pure and wasm-compatible; it may use `ids`, `diagnostics`, `quantity`, `fields`, `library` and `model` (narrowed to what S1 imports; later slices widen the row when they need `instances` or `completeness`). `updates` (0–16) and `commands` (0–17) widened to include it.

- `entries(&Project, &Drafts)`: one `CatalogEntry` per component lineage at its latest published revision, then lineages that exist only as drafts (`revision: None`, not placeable). An entry holds the source (`project`), name, description, the effective default of each selected field (component default, else field default) formatted in core, package names as labels, separate badges (symbol, footprint, 3D envelope, MPN — set from S2 when a Part pins the component) and the number of instances using the lineage.
- `Index`: entries plus their folded text and the `Vocabulary` (latest field revisions and their quantity kinds). `search` and `facets` run over it; `inspect` reports one revision with its revisions, symbols, implementations and footprints.
- `synthetic`: original fixture data (`EX-R0603-10K0-F`, `EX-C0402-100N-16V`, `EX-HDR-1X2-001`, …) for tests, the benchmark and trying the palette. It is not a starter library.
- **Deviation from the proposal:** the RKM pre-pass lives in `catalog` (`catalog::rkm`), not in `quantity`, so property entry is unchanged in S1. It is a pure function over a `UnitSet` and can move to `quantity` if property entry adopts it.

**Engine.** `Query::Search { query, limit?, include_drafts? }` (`library.search`), `Query::Facets` (`library.facets`) and `Query::InspectLineage { lineage, revision? }` (`library.inspect`) go through `Engine::query_with(query, &CatalogContext)`; `Engine::query` passes an empty context. Parse errors are `invalid_input` with the term in the message. Queries change neither the document, its revision nor history. CLI `stdio` and MCP reach them through `project.query`, with generated schemas.

**Desktop.**

- **Place palette** (Schematic; the ribbon's Place or the P key, which does nothing while a popup is open): a floating search sheet adapted from Solidcraft's command search, with its edge-to-edge key-hint footer. Type to search; ↑/↓ move; Enter places the highlighted revision with `component.place`, one undo step, at the free 5 mm grid point nearest the view centre whose symbol bounds (body and pin ends plus a 2.5 mm margin) clear every drawn symbol and stay inside the visible canvas, which excludes the Browser and properties cards; Shift+Enter places and keeps the palette open; clicking a row picks it for the Place tool (click the sheet to place); Esc closes. A row whose component has no symbol unit keeps the palette open with "… has no symbol to place." and places nothing; the footer drops the Enter hints whenever nothing can be placed. Each opening and each new query starts the list at the top with the highlighted row in view. Rows show the name with the first matching free-text term highlighted, key field values, the package, `project rN` and four separate badges (`sym`, `fp`, `3D`, `—MPN`); only the highlighted row takes the accent, hover is a neutral wash. Parsed chips and "N hidden" sit under the field (the row is omitted when empty); parse errors and "No component matches." are inset like the group captions. The properties card previews the highlighted row from `library.inspect` (revision, fields, symbol, package envelope, footprint pads, provenance). Recent picks rank higher for the session; they are not persisted until S3. Placed parts take the next free designator under their component's prefix (R1, C1, J1, …), which the core assigns.
- **Browser filter:** a compact search field (zoom icon, proportional text, clear button; Esc clears a non-empty filter) under Components keeps the `library.search` matches (drafts included) in rank order. The Components count reads "shown of all" while a filter is active, so it is visible from every workspace. A text that does not parse shows its error in the palette's error look and keeps the rows of the last text that did. More than 500 matches show the best 500 with "Showing the best 500 of N matches". Both fields bound their text to the core's 512-byte limit, so multi-byte units such as Ω count by bytes.

**Evidence.** Core unit tests cover `4k7`, `4.7k`, `R47`, `4R7`, `4n7` and `100nF`, `R` only where the unit set declares it, `V>=10k` (also through the engine and JSON), unit-key and field-name-key readings, key resolution that does not change when a field named `Voltage` or `Rated power` exists, unknown, ambiguous and reserved keys, ranges, tolerances, filters, ranking determinism under shuffled input with every tier and boost, facets, hidden drafts and `library.inspect`.
