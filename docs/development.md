# Development

How Sparksmith is built, checked and driven from the command line. The [README](../README.md) describes the product; this page is for contributors and for anyone scripting it.

PCB design software in Rust, using Solidcraft's egui/wgpu UI and native parametric engine. Component authoring, multi-sheet schematics, PCB layout and production output share one desktop shell. PCB 3D displays physical copper and package models through Solidcraft, with shared selection and whole-net highlighting.

This is an early working editor foundation, not a manufacturing-ready release. See [current evidence and limits](editor-evidence.md).

## Build and run

`rust-toolchain.toml` pins Rust 1.96.0, Clippy, rustfmt and the wasm target. Use rustup, or the Nix dev shell, which provides exactly that toolchain:

```sh
nix develop          # optional: pinned toolchain without rustup
cargo run --locked --profile ci -p sparksmith [FILE.sparksmith]
cargo xtask ci
```

The app starts with an empty project (as File › New does); open a project, or write the showcase with the CLI below. Component authoring includes Symbol, Footprint, Mapping and 3D modes; each finished edit of the five component drafts (component, symbol, package, footprint, binding) is one undo step, and Publish creates immutable project revisions. In Schematic, Place (or P) opens the Place palette: type a query such as `10k 0603`, `res>=10k` or `tol<=1%`, move with ↑/↓, press Enter to place (Shift+Enter keeps the palette open) or click a row to place it with the mouse; the properties card previews the highlighted part. Connect terminals with Wire and rename a selected wire's net. The Browser's Components section has a filter field that uses the same search. In PCB, preview/apply Update PCB, move placements and route between pads. Switch between 2D and 3D within PCB; selection and whole-net highlighting are shared.

File offers New, Open, Save, Save as and Export to Solidcraft through native dialogs; reads, writes and exports run in the background. Unsaved work is snapshotted for crash recovery and offered at the next launch. Project files contain the revisioned library snapshot and the definition drafts, so they reopen offline. Native export writes a new parametric `.solidcraft` file; package models are clearly identified envelopes.

Per-user files (settings, keymap, fab and AI profiles, live-MCP tokens) live in the config folder `sparksmith` (`~/Library/Application Support/sparksmith`, `%APPDATA%\sparksmith`, `$XDG_CONFIG_HOME/sparksmith` or `~/.config/sparksmith`), the library index cache in the platform cache folder `sparksmith`, and recovery snapshots in `~/Library/Application Support/Sparksmith/Recovery`, `%LOCALAPPDATA%\Sparksmith\Recovery` or `$XDG_STATE_HOME/sparksmith/recovery`. `SPARKSMITH_CONFIG_DIR`, `SPARKSMITH_CACHE_DIR` and `SPARKSMITH_RECOVERY_DIR` move them. The names come from `sparksmith_core::product`. On the first start after the rename from Pcbcraft, the app and the CLI copy the former `pcbcraft` config folder and `Pcbcraft`/`pcbcraft` recovery folder to the new names when the new folder does not exist yet; the former folders are kept unchanged and the cache is rebuilt ([rename](rename-phase-b.md)).

Navigation: scroll zooms; middle-drag pans; right-drag orbits in 3D. Cmd/Ctrl+S saves, +Shift+S saves as, +O opens, +N starts a new project, +Z/+Shift+Z undo and redo.

## Architecture

| Crate | Responsibility |
| --- | --- |
| `sparksmith-core` | Pure, wasm-compatible document: revisioned library definitions and drafts, component instances and symbol occurrences, schematic, persistent nets, layout, impact plans, completeness findings, typed `Operation`s and `Query`s, the one `Engine` (shared undo, engine-owned drafts), file format, typed errors and check findings. |
| `sparksmith-io` | Bounded reads, atomic writes, crash recovery. |
| `sparksmith-solidcraft` | Builds the native Solidcraft model through a typed facade over Solidcraft's command API. |
| `sparksmith-kicad` | KiCad board import, slice K1: footprints, pads (every shape, custom pads, mask, paste and drills) and their placement, built into a new project through the one engine, with an import report of what is exact, approximated, reported or refused. It reads the bytes it is given. |
| `sparksmith-fabcheck` | Development only (a dev-dependency and `xtask`): Gerber and Excellon readers, exact polygon comparison in integer nanometres (difference area, widest piece), drill-hit pairing, and `kicad-cli` run as a black-box oracle on a temporary copy. |
| `sparksmith-firmware` | Pin-configuration exports from the core's pin report (JSON, C header, Zephyr overlay skeleton, Rust constants); pure text, beside `sparksmith-io`. |
| `sparksmith-automation` | Headless `Session` (engine + open/save/export) shared by the JSON-lines transport and the MCP server, and the live channel into the open window ([live MCP](#live-mcp)). |
| `sparksmith-assist` | The datasheet assistant: a tool loop over the automation session that drafts a part from its datasheets, on a model you configure (Anthropic Messages or any OpenAI-compatible endpoint, hosted or local), with token, time and request caps ([as built](datasheet-assistant.md)). |
| `sparksmith-ui` | The UI toolkit the desktop draws with, seeded from SolidCraft's MIT/Apache interface code (UI kit, theme tokens, icons, fonts) as of `a34756830` (see [attribution](../ATTRIBUTION.md#the-ui-toolkit-seed-cratesui)). |
| `sparksmith`, `sparksmith-cli` | Desktop editor and command line (its binary is `sparksmith`). |

`cargo xtask layers` enforces this direction; `cargo xtask ui-containers` rejects raw egui windows, areas and panels outside the kit's `ui_kit::Container` (SolidCraft's, vendored in `crates/ui`). `cargo xtask core-modules` enforces the core module map in [component model](component-model.md), and `cargo xtask connectivity` that only `layout/connectivity` decides whether copper joins ([copper graph](copper-graph.md#where-connectivity-lives)). `cargo xtask f64-lengths` rejects new serialized `f64` length fields in the core's `model`, `library` and `geometry` modules: stored lengths are `units::Nm`; its allow-list holds the fields the units migration has yet to convert, and only shrinks. `cargo xtask format-lock` fails when the saved document's schema (derived from the core's stored types, `sparksmith_core::format::stored_schema`) no longer matches the fingerprint committed in `crates/editor-core/format.lock` while `FILE_VERSION` and the named features are unchanged; doc comments and Rust type names do not count, field names, types, tags, defaults and field order do. An incompatible change raises `FILE_VERSION`, adds a step to the converter chain (`sparksmith_io::convert::STEPS`) and a golden file under `crates/io/tests/fixtures/format/`, then records the lock with `cargo xtask format-lock --update`, which refuses while the version and features are as locked ([versions](#file-versions)). `sparksmith convert FILE…` rewrites older files in place, keeping the original as `FILE.v<N>`. `cargo xtask licences --check` rejects dependencies that require GPL-family or unreviewed licenses, `cargo xtask brand-crates` rejects SolidCraft's brand-licensed crates (`solidcraft-ui-kit`, `solidcraft-look`, `solidcraft-theme`) and `solidcraft-ui-egui` anywhere in the dependency graph, and `cargo xtask clean-room` rejects EDA library files and data in the repository. `cargo xtask no-builtin-data` (alias `no-builtin-parts`) rejects `include_str!` and `include_bytes!` in non-test program code, except the interface assets, the MCP skill prompt and the sites its allowlist marks as being moved ([generator plugins](generator-plugins.md#gate-no-built-in-data)); library data ships in `library/`. `cargo xtask generic-terms` rejects product-specific words for a linked design (an example use case, such as an enclosure) in any path or text file under `crates/`, `apps/` and `xtask/`; it has no allow-list, and such examples belong in prose under `docs/`. All of these run in `cargo xtask ci`.

## File versions

The project file carries a format `version` (`sparksmith_core::format::FILE_VERSION`, 3 since 14 November 2026: part-generation slices B1–B4) and, when it uses any, the named optional `features` it uses ([plan §4.7](design/file-format-plan.md#47-versions-and-migrations)). The project tree that replaces the single document, its two layouts and its encoding rules are specified in [the file format](file-format.md).

- **Every incompatible change raises the version.** `cargo xtask format-lock` catches a stored type that changed without one. A change that only adds an optional capability may instead add a name to `format::FEATURES` and its test to `format::features_used`: a file lists a feature only when it uses it, so designs without it stay readable by older builds, and a build refuses a feature it does not know, naming it.
- **Converter chain.** `sparksmith_io::convert::STEPS` holds one pure step per version, each rewriting the document's JSON from N to N + 1 (step 1 to 2 is the former `cargo xtask convert-v1`: the units migration so far and fab profiles as files; step 2 to 3 makes part-file values integers and detaches generated parts of the old generator ABI, saying how many). After the steps the file is read as the app reads it, its remembered hashes are recomputed, and it is written as the app writes it.
- **Before the first release** the chain runs only as `sparksmith convert [--profile PROFILE.json] PATH…`. The app opens only the current version; an older file is refused with that command named, a newer one as "from a newer Sparksmith". The same command converts library folders, replays and old profile files with the units conversion in place (original kept as `.pre-nm`); their formats have no version step yet.
- **Golden files.** `crates/io/tests/fixtures/format/v<N>/demo.sparksmith` holds the same small original design (`Engine::demo`) for every version, never regenerated once committed. Each old golden converts to the current golden byte for byte; the current golden opens and saves byte for byte. When the version rises, `cargo test -p sparksmith-io --lib write_missing_golden_files -- --ignored` writes the new golden by converting the previous one; check it before committing.

Named features so far: `pad_fill_overrides` (a part's or pad's fill override), `parts_without_terminals` (a component or package without terminals that no part file models), `board_only_parts` (an instance on the board only), `project_rule_source` (the project's own rule set names its source), `pins_added_by_import` (a symbol pin an import added for an unmapped pad) and `net_disagreements` (where an imported board and its schematic disagreed on nets).

To raise the version: change the types, raise `FILE_VERSION`, add the step to `STEPS`, write the new golden, convert the files in `examples/`, then run `cargo xtask format-lock --update` and commit `crates/editor-core/format.lock` with the change.

## CLI, JSON lines and MCP

```sh
cargo run --locked --profile ci -p sparksmith-cli -- showcase example.sparksmith   # a routed 4-layer board with via examples; open it in the app
cargo run --locked --profile ci -p sparksmith-cli -- convert old.sparksmith   # an older format version to the current one, in place; the original is kept as old.sparksmith.v<N>
cargo run --locked --profile ci -p sparksmith-cli -- parts parts.sparksmith   # 24 invented EX- parts for the Place palette
cargo run --locked --profile ci -p sparksmith-cli -- sample-library NEW_DIR [NAME]   # the same catalog as a library folder
cargo run --locked --profile ci -p sparksmith-cli -- export example.sparksmith example.solidcraft
cargo run --locked --profile ci -p sparksmith-cli -- fab example.sparksmith out/   # production check, then Gerber X2, Excellon, job, pick-and-place, BOM and PDF drawings
cargo run --locked --profile ci -p sparksmith-cli -- export-schematic-pdf example.sparksmith example.pdf [--sheet ID]...   # vector PDF, one page per sheet
cargo run --locked --profile ci -p sparksmith-cli -- commands
cargo run --locked --profile ci -p sparksmith-cli -- stdio [--permission-mode MODE] [--allow-folder DIR]... [FILE.sparksmith]
cargo run --locked --profile ci -p sparksmith-cli -- stdio --operator [FILE.sparksmith]
cargo run --locked --profile ci -p sparksmith-cli -- mcp [--permission-mode MODE] [--allow-folder DIR]... [FILE.sparksmith]
cargo run --locked --profile ci -p sparksmith-cli -- mcp --live [--port PORT]   # the project open in the desktop window
ANTHROPIC_API_KEY=… cargo run --locked --profile ci -p sparksmith-cli -- design-part \
  --datasheet PART.pdf --name PART --out part.sparksmith   # drafts + PART.review.md; publishes nothing
cargo run --locked --profile ci -p sparksmith-cli -- design-part --provider openai \
  --base-url http://localhost:11434/v1 --model MODEL --context-tokens N --vision yes \
  --datasheet PART.pdf --name PART --out part.sparksmith   # the same on a local model
```

`stdio` reads one JSON request per line (4 MiB maximum) and answers `{"ok":true,"result":…}` or `{"ok":false,"error":{"code":…,"message":…}}`. `project.apply` takes the same typed operations as the UI with an expected revision; `project.inspect`, `.undo`, `.redo`, `.new`, `.open`, `.save`, `.preview_update`, `.apply_update` and `.export_native` share the session. `mcp` serves the same requests as MCP tools (`project_apply`, …) over stdio. `commands` prints schemas generated from the Rust types.

Replies on both are compact: a mutation answers with `revision`, `outcome`, `changes` (added, changed and removed stable ids by collection, such as `{"added":{"vias":[644]}}`), `findings` (the new ones, resolved counts per code, the open total) and the changed `drafts`. `project.inspect` answers with counts, drafts and findings per code, and with `at` (a JSON pointer such as `/project/nets`) reads one piece of the document. `verbose: true`, beside `command` or inside `params`, returns the whole snapshot instead. In MCP, `tools/list` names every operation and query, and `project_schema {name}` (`project.schema`) returns one's exact schema and how to send it. `prompts/list` offers the workflows: `datasheet_to_component` (arguments `part`, `datasheets`, `notes`) is the [datasheet-to-component workflow](datasheet-assistant.md#mcp-workflow), served from `skills/sparksmith-datasheet-part/SKILL.md`.

Every command has a permission class: read, edit, ask or never, shown in its tool description and in `project_schema`. `Session::respond` enforces the class for every model-facing transport (headless MCP, live MCP and `stdio`): the never class is always refused, and so is a path outside the run's folders. `mcp` and `stdio` are gated alike, because Sparksmith cannot tell a script from a model; `--permission-mode` chooses how: `ask-every-time` runs only reads, `auto-allow-edits` (the default) also runs edits, and `allow-all` runs everything except the never class. Neither has a way to ask, so whatever would need asking is refused with a message saying so; `--permission-mode allow-all` is the operator's explicit choice to let ask-class requests run. Under any mode, a path must be absolute and inside an `--allow-folder` or the folder of the project named on the command line. `stdio --operator` says you are running it yourself, not a model: every class runs, including library sources and settings, with any path, as at the command line. It takes no mode or folders, and `mcp` does not accept it. Your own replays use it (`examples/esp32-s31-devboard/regenerate.sh`).

### Live MCP

An assistant can also edit the project open in the desktop window, so you watch each change and share one undo history. In Sparksmith, choose **Help › Connect AI assistants…** (also in the in-window File menu and the command palette) and turn on **Let AI assistants edit this project**. It is off at every start. The window shows the configuration to copy:

```json
{"mcpServers": {"sparksmith": {"command": "/path/to/sparksmith", "args": ["mcp", "--live"]}}}
```

For Claude Code: `claude mcp add sparksmith -- /path/to/sparksmith mcp --live`.

- **Connection.** The window listens on `127.0.0.1` only, from port 27979 (or the next free one), using Solidcraft's control channel. Each time you turn it on, it makes a new token and writes it to `control/PORT.token` in the Sparksmith config folder, readable only by you; `control/current.port` names the port. `sparksmith mcp --live [--port PORT]` reads both, so the configuration holds no secret. `SPARKSMITH_CONTROL_TOKEN` gives a token explicitly. Turning access off, or closing the window, closes every connection and removes the files.
- **Same engine.** Requests run on the UI thread, between frames, through the same `Session::respond` as the headless server, on the window's engine. The tools are the same, except that `project_new`, `project_open` and `project_save` are left to you in the window. Replies stay compact: a via placed on the demo answers in under 4 KB.
- **Revisions.** Every tool that changes the project takes `expected_revision`, inside its parameters or, for tools such as `project_undo` that have none, beside them. A stale revision is refused with `stale_revision`, so the assistant inspects again.
- **Refusals.** While you type in a field, drag, or have a menu, the command palette, a file question or an update review open, a change is refused with `live.busy` and the reason. Reads still answer.
- **Permissions.** The window's choice (reading only; reading and edits, the default; or everything except settings) decides as `--permission-mode` does. An ask-class tool, such as an export, waits for **Allow** or **Deny** in the window; the never class is refused. Paths must lie in your home folder, the temporary folder or the project's folder.
- **What you see.** The application bar shows *AI access on* or *AI assistant connected* while access is on; its × turns access off. Each assistant edit shows as a toast with Undo and a Messages line (*AI assistant edit: layout.add_via*), and undoing one says *Undid AI assistant edit*.

`project.query` also answers the parts catalog ([design and query language](parts-library.md)): `library.search` ranks the project's component lineages for a one-line query, `library.facets` lists the fields, packages and badges the matches carry, and `library.inspect` reports one revision. For example:

```json
{"command":"project.query","params":{"query":"library.search","params":{"query":"res>=10k pkg:0603","limit":10}}}
```

Field keys come from the project's field names and units, so a query reports `V>=10k: 10 k has no unit of voltage` rather than guessing.

Library folders ([S3](parts-library.md#s3-as-built)) are plain directories of immutable revision files, shareable through git. `library.source.add` lists one in the user's settings (`SPARKSMITH_CONFIG_DIR`, `SPARKSMITH_CACHE_DIR` override the platform directories); `library.search` then includes its entries, `library.place_from_folder` imports and places in one undo step and `library.publish_to_folder` promotes a project revision to a writable folder. Imported revisions keep their origin and attached copies, so projects reopen without the folder. `library.import_from_project` copies one published revision and its closure from another `.sparksmith` file, as one undo step.

## Board parity

The board's flat bodies (laminate slabs, pad, track, via and fill copper) are described once by the board plan (`sparksmith_solidcraft::project::plan`): each body's kind, source object, layer, z span, outline loops and look, as pure data read from the document. The exact native build makes each of them from the plan. `cargo xtask board-parity` builds every example board under `examples/` and checks, body by body:

- the build against the plan by geometry fit (`plan::parity`, slice G1): each planned body built once, of its kind, source and layer; its top and bottom faces, read from the B-rep's face loops (each edge's own curve sampled to 0.1 µm, `project::fit`), against the plan's loops flattened to the same tolerance: the exact area where they differ (their symmetric difference on a nanometre grid) no more than their length times both tolerances, every point within 1 µm of the other outline, and the same number of holes; its heights within 1 µm; and, for copper, its volume within 1 ppm as one more sign. Laminate slabs are checked by outline like copper (their holes may cross, as a via ring through a track's cut in a foil level: the plan's loops nest by containment, crossing holes uniting). No flat body may be built that the plan lacks. Measured on the ESP32-S31 example (`export_tiers`, 13 November 2026, loaded machine): every outline within 0.102 µm of its plan, at most 0.0096 mm² between them on a whole slab; the check took 2.3 s of a 14.6 s mechanical export and 9.5 s of a 36.3 s full one;
- every native body against the record in `crates/automation/tests/board_parity/<board>.jsonl` (box to 1 nm, volume to 1 ppm), made from the build before the plan existed.

- the live view's meshes against the plan (`mesh::parity`, `example_boards_mesh_as_their_plan`): one mesh per plan body, of its kind, source and layer, the laminate drawn whole (`BoardPlan::whole_laminate`); each box within the flattening tolerance (2 µm), each volume exact on its flattened loops (1 ppb) and within flattening (loop length × 2 µm × thickness) of the plan body's exact volume. It needs no build, so the workspace tests run it too.

A change meant to change the built bodies rewrites the records with `SPARKSMITH_BLESS_PARITY=1 cargo xtask board-parity`; say so in its commit. CI runs the exact-build check once, after the workspace tests, which leave it out (it is an ignored test).

The 3D view always uses the direct mesh (`Flat::Meshed`; stage A4 removed the setting and the live native board): no design of the board is made. The flat bodies are meshed from the plan (`project::mesh`, with a per-body memo), and each part is its package revision's own Solidcraft design (`project::designs`), evaluated once, kept between models and shared by every placement, drawn where the document's transform puts it (`interface::package::model_to_board`). The model worker keeps the last model only and makes every next board (an edit, an undo or redo, a refill) from what it kept (`project::update`). A meshed model is never saved; exports build the exact model, which is never updated in place. `cargo xtask board-parity` also checks every example board's parts in the live model against the exact build's solved joints (`designs::parity`: every vertex within 1 µm); the workspace tests check every kind of part model on both sides at every turn (`project::designs::tests`).

**Exports (stage A5).** `sparksmith_solidcraft::export::board` is the one export of the exact board: File › Export to SolidCraft…, `project.export_native {path, tier?}` and `sparksmith-cli export FILE NEW_FILE [--tier mechanical|full]` all call it. Tier `mechanical` (the default) is the laminate, the pads and the parts; `full` adds every track, via and fill; `interface` is published only (`interface.publish`). The build counts each Solidcraft command on an `export::Watch` and says its stage (building, evaluating, checking, saving); `Watch::cancel` stops it at the next command or checked body with `Cancelled`, writing nothing (the board's evaluation and the save are single commands and run to their end first; a save that ends after the cancel is removed). Before writing, every flat body is checked against the board plan the build read by geometry fit (`plan::check`, the same comparison as `plan::parity`, slice G1). A model that does not fit is refused by default and nothing is written: `Error::Unfit`, code `export_unfit`, whose message names each body in the user's words ("Track 12 on the top layer: its track copper was built in another shape: its outline is off by up to 0.0500 mm (0.1000 mm² differs)"; a slab is "The laminate from z 0.165 to 0.200 mm", with its holes counted where they differ). `project.export_native {write_anyway: true}`, `sparksmith-cli export … --write-anyway` and the window's "Write the file even if bodies do not fit the board" (off each time it opens) write it all the same; the report then lists each body planned and not built, or built and not planned, with its object, kind, layer, box, volume and fit (`check.differences[].fit`: difference area, deviation, holes, heights), and `check.max_deviation_mm` and `check.max_area_mm2` say how close the bodies that fit came. The file is written to a hidden sibling first and linked into place, so an existing file is never replaced. A mechanical or full `interface.publish` reports the same check for its section 2 (`published.check`) and writes its files all the same. In the app the export runs on its own thread, so saving, recovery and editing go on; its window shows the stage, the commands run and Stop. `cargo test -p sparksmith-automation --profile ci --test export_tiers -- --ignored --nocapture` measures both tiers on the ESP32-S31 example.

## KiCad import comparison

`sparksmith import-kicad DIR|FILE.kicad_pcb NEW_FILE.sparksmith [--profile ID]` imports a KiCad board (a folder names its one board; its `.kicad_pro` is read when present) through the one command engine with SolidCraft's sketch engines, on the fab profile library's profile, and saves it. It prints the import report's counts and writes its detail (designators, pads, net names) beside the new file as `NEW_FILE.kicad-import.json`. A board whose fill copper would outgrow the 16 MiB file bound is saved with its fills defined and unfilled; fill copper is derivable and refilled.

`cargo xtask kicad-compare --design PATH` (or `SPARKSMITH_KICAD_DESIGN`) imports every `.kicad_pcb` of a design, writes our fabrication files and compares their copper (pads, tracks, vias and zone fills; KiCad's copper drawings are left out), mask, paste and drill hits with KiCad's own plots to 1 µm (drill hits to 1 µm plus the √2 µm two files written to 1 µm may round apart), and the board outline with KiCad's `Edge.Cuts` plot (the widest distance of its centre lines from our solved outline). The gates never build Solidcraft, so run it as `cargo run -p xtask --features sketch -- kicad-compare …` to import the outline as a board sketch, as the CLI and the app do; without the feature the outline is the rectangle around it. Our board origin is the outline's lower-left corner, in whole micrometres (our outlines lie right of and above the origin), so KiCad's plots, taken about the drill and place origin, are moved onto ours before comparing. Nets come from the schematic when the board's folder holds its root `.kicad_sch` (the board's stem): each sheet instance becomes a sheet under a sheet symbol with its pins; each footprint's part gets a symbol with KiCad's units, body and pins where KiCad has them (a pad no pin names, an unmapped pad, gets a visible pin on the body's right side marked "added by import" and an "unmapped pad" finding, counted; the person keeps it by clearing the mark in the pin's card or waiving the finding, or moves or deletes it), placed and turned where KiCad has it; then KiCad's wires (with their corners, joining where KiCad joins them), junctions, labels, power symbols, hidden power inputs and no-connect flags are drawn with the schematic commands. KiCad's wire pieces are drawn as strokes; where wire ends meet at a point (four ends with a junction, say), the first stroke runs through it and every other one ends on it, since our crossing wires do not join. KiCad ties a symbol pin to the pad of the same number; the importer resolves that tie once into the binding, so pin mapping stays explicit. Pins of type "not connected" join nothing. KiCad lets one net carry several label names and compares names exactly; ours carry one and compare without case, so names joined by wires take the net's one name (power and global first) and names differing only in case are spelled apart. The summary then compares the schematic's nets with the board's, net for net (equal, split, joined with another). Where they disagree the schematic wins, and each disagreement is kept in the project (`schematic.set_net_disagreements`) as a finding while the schematic still disagrees: a board net whose terminals the schematic keeps apart ("joined on the imported board") and a schematic net whose terminals the board has on several nets or on none ("split on the imported board"); waiving one keeps the schematic's net. A footprint without a symbol, and a board without a schematic, get a local label of the board net's name on each pin instead. Zones become fills per copper layer (net, outline, priority, clearance, least width, pad connection, thermal gap and spoke width, island removal) and rule areas, footprints' included, keepouts; our engine fills them. A footprint's and a pad's zone overrides (connection, spoke width and angle, relief gap, clearance) become the part's and the pad's fill overrides (`fill.set_pad_override`). Track pieces shorter than the engine's least track length (0.01 mm) are removed and the ends they joined meet at one point (a via's centre when one is there), so nothing dangles; the report counts them. A footprint without electrical pads (a fiducial, a mounting hole) becomes a part without terminals, and one KiCad marks "not in schematic" a board-only part (`component.place_board_only`). The project file's rules become the project's own rule set, marked "From the KiCad project" (`rules.set_project_source`), over the fab profile, which keeps the fab limits: the default class's clearance, track width and via size and the board minimums (edge, hole and hole-to-hole clearances, least track width, annular ring, drill and text height) as overrides, except limits looser than the profile's, which stay out and are counted ("N KiCad rules looser than the fab profile were not taken" in the import report); every other class as a net class (clearance, track width, via size, differential-pair width and gap) with its plain-wildcard name patterns, and nets assigned explicitly where KiCad assigns them or where our net names would not match the pattern. They are set after the tracks and vias go in (which the file has as they are) and before the fills. Each board then lists the board checks' findings, counted by code. Each layer prints our-only and KiCad-only areas. KiCad's plots come from the installed `kicad-cli`, run on a copy in the ignored `target/kicad-compare/<run>/`, which is deleted after each plot; no tool runs in the design folder, and the design is never written. The summary prints counts, areas and widths only; names and locations stay in each board's local `report.json`. Pieces on round custom-pad primitives, and on the round joins of grown or shrunk custom-pad openings, that KiCad draws as chords may be 6 µm wide (its default maximum error and 1 µm). Mask and paste openings are true offsets in both tools: a grown sharp corner is rounded by the growth. `cargo test -p sparksmith-kicad --test oracle -- --ignored` with `SPARKSMITH_KICAD_ORACLE=1` runs the same comparison on Rust-built synthetic boards; CI runs the synthetic tests without KiCad.

## Footprint wasm proof

To execute the footprint evaluator's golden-hash tests (native/wasm agreement) as WebAssembly under Node (rather than only compile wasm), install Node and the test runner matching the locked `wasm-bindgen` version:

```sh
cargo install wasm-bindgen-cli --version 0.2.129 --locked
cargo xtask wasm-footprint
```

Run these inside `nix develop` when using the Nix toolchain. The runner must be on `PATH`, or set `CARGO_TARGET_WASM32_UNKNOWN_UNKNOWN_RUNNER` to its executable path. This optional runtime check is separate from `cargo xtask ci`; it does not exercise browser UI.

Solidcraft and its required patches are pinned to `64bebfef0a77dab8c79666114c7601c9dda55d12` of the [DAmesberger/solidcraft](https://github.com/DAmesberger/solidcraft) fork (branch `pcbcraft-smlib-open`): upstream Solidcraft `a34756830` with its SMLib kernel (`solidcore`, vendored in Solidcraft), plus material graphs on upstream's shared viewport renderer with an instanced graph draw, which the PCB 3D view uses for the board's look, and via scaling (indexed profile nesting, batched copies and joints, instanced display, deferred evaluation); Solidcraft's own app is unchanged by default, except that bundled symbols now draw ahead of the system language fonts. Builds use git dependencies and the lockfile; a neighboring Solidcraft checkout is not required. The native probe and copper sample (vias, zone with hole, same-net island) are acceptance tests in `sparksmith-solidcraft`, not product features. UI source references and font licenses are recorded in [attribution](../ATTRIBUTION.md).
